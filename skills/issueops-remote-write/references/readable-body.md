# 사람이 읽는 이슈·PR 본문 작성 지침

이슈와 PR은 팀원과 리뷰어가 읽는 문서다. 본문에는 사람이 전체 흐름을 파악하는 데
필요한 내용만 둔다. plan·spec·intent·게이트 같은 구현 자료는 `.issueops/issues/<n>/`에,
해시·커밋 SHA·실행 기록은 record에 둔다.

절 구성의 원본은 `issueops remote render-template`이다. 이 문서는 절을 **어떻게 채우는지**만
다룬다.

## 공통 규칙

1. **첫 절은 `## 요약`이다.** 2~3문장으로 쓴다.
   - 이슈: 무엇이 문제인지, 왜 지금 고치는지, 끝나면 무엇이 달라지는지.
   - PR: 무엇을 왜 바꿨는지, 그 결과 무엇이 달라지는지. 마지막 줄에 `Closes #n`을 둔다.
   - 하위 작업: 부모 이슈 링크와 이 작업이 맡는 부분.
2. **필수 절은 골격 순서대로 둔다.** 필수 절 사이에 절을 더해도 된다.
3. **선택 절은 쓸 내용이 있을 때만 만든다.** "없음"만 적은 절은 두지 않는다.
4. **사실과 추정을 나눈다.** 원인이 추정이면 추정이라고 쓴다. PR에는 확인하지 못한 것을
   따로 적는다.
5. **하네스 기록은 쓰지 않는다.** 해시, 커밋 SHA 전문, 라벨 점수, 정리 감사, 에이전트
   사이의 지시, plan·spec 원문, 로컬 절대 경로를 본문에 넣지 않는다.

## 구조는 explain을 따른다

- **이슈**는 계획을 설명하는 순서로 쓴다: 문제 → 방식 → 근거 → 대안 → 검증.
- **PR**은 작업을 보고하는 순서로 쓴다: 바뀐 결과 → 확인한 것 → 확인하지 못한 것 → 남은 일.
- **진행 결과**는 작업 보고를 줄인 형태다(아래 절).

절별로 채우는 내용은 다음과 같다.

| 절 | 내용 |
|---|---|
| 배경 | 누가 어떤 상황에서 무엇을 겪는지. 입력과 출력, 수치, 로그 한 줄 같은 구체적인 장면 하나. 코드 근거는 그 뒤에 짧게 |
| 범위 | 하는 것과 하지 않는 것을 함께 |
| 완료 기준 | 확인할 수 있는 동작. "적절히 처리된다" 같은 판단할 수 없는 문구는 쓰지 않는다 |
| 검증(이슈) | 제목은 `## 검증` 그대로. 첫 코드 블록에 실행할 검증 명령을 둔다 |
| 확인한 것(PR) | 확인한 동작, 확인 방법, 결과. 결과를 "pass"로만 쓰지 않는다. 확인하지 못한 것은 따로 |
| 리뷰 포인트 | 판단이 필요한 곳과 원하는 피드백의 종류 |

## 문장은 fluent-korean으로 다듬는다

초안마다 `fluent-korean` 스킬을 호출한다. 본문이 길면 그 스킬의
`references/slop-patterns.md` 절차까지 적용한다. 특히 다음을 지킨다.

1. 명사구나 목록 항목을 빼면 완성된 문장으로 쓴다. 서술어와 종결어미를 생략하지 않는다.
2. 단정을 피하는 어미를 쓰지 않는다. 불확실성이 실제로 있으면 근거를 함께 쓴다.
   - 나쁜 예: `해당 변경이 호환성 문제를 일으키지 않을 것으로 보여집니다.`
   - 좋은 예: `기존 클라이언트는 응답에 추가된 필드를 무시하므로 호환됩니다.`
3. 서론 선언으로 시작하지 않는다. 첫 문장이 문제 정의나 요구 사항이다.
   - 나쁜 예: `이 이슈에서는 배포 실패 문제를 다루고자 합니다.`
   - 좋은 예: `v2.3 배포가 시크릿 누락으로 실패합니다.`
4. 정보가 없는 수식어(`효율적인`, `전반적인`, `개선된`) 대신 무엇이 어떻게 바뀌는지 쓴다.
5. 같은 개념에는 한 용어를 유지한다. 워커와 worker를 섞어 쓰지 않는다.
6. 명령어, 코드 식별자, 경로, URL은 영어 원문을 유지하고, 나머지 서술은 한국어로 쓴다.

## 용어 변환표

| 하네스 용어 | 본문에서 쓰는 말 |
|---|---|
| canonical worktree | 작업 공간 |
| active owner, holder | 담당 세션 |
| release, handoff | 작업을 넘긴다 |
| readback | 게시한 뒤 다시 읽어 확인했다 |
| devil's advocate | 계획 검토 |
| G1~Gn, gates | 검증 항목 |
| brooks, turing 같은 리뷰 에이전트 이름 | 역할 이름(독립 리뷰, 검증 루프) |
| lease, generation, 봉인, fingerprint | 쓰지 않는다 |

issueops 자체를 다루는 이슈처럼 이 용어가 주제인 경우에는 처음 나올 때 한 문장으로
설명하고 쓴다.

## 모범 사례

공개 사례만 쓴다. 비공개 저장소의 문장과 수치는 옮기지 않는다.

- 이 저장소의 PR #495: 첫 문장이 요약이고, 절 제목이 독자의 질문을 따른다("원인",
  "고친 것", "같은 실패가 반복되지 않게", "남는 위험").
- 이 저장소의 PR #489: 요약, 결함, 변경, 검증, 호환성 다섯 절로 끝난다.
- Go 제안 #60078: 첫 문장이 곧 결정이다.
- 리눅스 커널 submitting-patches 문서: 해결책보다 문제를 먼저, 구체적인 장면으로 보인다.

새 계약으로 쓴 PR의 예는 다음과 같다.

```markdown
## 요약
두 이슈를 서로 다른 세션에 동시에 맡겨도 서로 간섭하지 않는지 실제로 돌려
확인했고, 결과를 보고서로 남깁니다. 런타임 코드는 바꾸지 않았습니다.
Closes #510

## 변경 내용
- 병렬 실행을 관찰한 보고서를 추가했습니다.

## 확인한 것
- 두 사이클이 서로 다른 프로세스에서 동시에 활성 상태를 유지했습니다(실제 실행).
- 작업을 넘긴 세션의 요청은 거부됐고, 기록은 바뀌지 않았습니다.

## 리뷰 포인트
- 보고서의 판정이 관측 기록과 맞는지 봐 주세요.
```

## 진행 결과

사이클이 머지된 뒤 정리 단계가 이슈 끝에 붙이는 구간이다. 원고는 임시 파일로 쓰고
`issueops remote reflect-completion --body-file`로 넘긴다.

- 결과 1~2문장과 흐름 3~6줄로 쓴다. 흐름은 계획, 검토에서 바뀐 점, 구현, 확인, 남은 일
  순서다. 구현 줄에 PR 링크를 넣는다.
- PR 본문과 record를 참고해 쓰고, 커밋 SHA 전문과 로컬 경로는 쓰지 않는다. 이 원고에서는
  두 값이 critical이고, 2,000자를 넘어도 거부된다.

```markdown
두 이슈를 서로 다른 세션에서 동시에 진행해도 서로 간섭하지 않는다는 것을
실제 실행으로 확인했습니다. 자세한 관찰 내용은 PR #512의 보고서에 있습니다.

- 계획: 갱신한 설치본으로 이슈 생성부터 완료 기록까지 한 사이클을 실행한다.
- 구현: 새 세션이 작업을 넘겨받아 보고서와 검증 기록을 작성했다(PR #512).
- 확인: 두 사이클이 동시에 진행됐고, 작업을 넘기기 전 세션의 요청은 거부됐다.
```

## 가독성 검사가 보는 것

게시·동기화 명령이 항상 실행한다. critical은 게시를 막고, warning은 preview에 줄 번호와
함께 나온다. 코드 블록과 inline code 안은 해시·경로·용어 검사에서 뺀다.

| 구분 | 코드 | 기준 |
|---|---|---|
| critical | `korean_ratio` | 코드·URL·경로를 뺀 문장에 한글 20자 이상, 한글 대비 영어 단어 1.2 이하 |
| critical | `summary_section_missing` | 첫 절이 `## 요약`이고 비어 있지 않다 |
| critical | `required_section_missing`, `placeholder_section` | 필수 절이 모두 있고, "없음"·"N/A"·"TBD" 같은 자리 표시만 담지 않는다 |
| critical | `sha256_hex` | 코드 밖에 64자리 hex가 없다 |
| warning | `summary_too_long` | 요약이 400자를 넘는다 |
| warning | `harness_term` | 코드 밖에 하네스 용어가 나온다 |
| warning | `local_path`, `commit_sha_full` | 로컬 절대 경로, 40자리 커밋 SHA 전문. 진행 결과 원고에서는 critical |
| warning | `empty_optional_section` | 선택 절이 비어 있다 |
| warning | `slop_pattern` | 단정 회피 어미, 서론 선언, 엠대시 3개 이상, 화살표(→) 3개 이상 |
| warning | `result_only_pass` | 확인한 것·검증 절에 "pass", "통과", "ok"뿐인 줄이 있다 |
| warning | `duplicate_sentence` | 같은 문장이 두 절 이상에 반복된다 |
| warning | `unrendered_field:<key>` | 본문에 렌더하지 않는 `--field`를 넘겼다 |

**warning 처리**: warning마다 고치거나, 남겨 두는 이유를 한 줄로 적는다(작업 보고나 PR의
리뷰 포인트). 이유 없이 넘기지 않는다.

## 독자 검토(권장)

맥락이 없는 subagent에게 제목과 본문만 주고 네 질문에 답하게 한다.

1. 무엇이 문제이고 무엇이 바뀌는가?
2. 왜 지금 필요한가?
3. 끝났는지 어떻게 확인하는가?
4. 모르는 용어나 두 번 읽은 문장이 있는가?

답이 `.issueops/issues/<n>/intent.md`의 해석·성공 기준과 다르거나, 모르는 용어가 하나라도
있으면 본문을 고친다.
