# IssueOps Explain

이 스킬의 일은 **끝난 작업을 사람에게 말로 설명하는 것**이다. 원격 본문이 아니라
대화로 하는 보고이며, 읽는 사람은 이 작업을 요청했지만 과정을 보지 않은 사람이다.

- 전체 흐름: [`issueops`](../issueops/SKILL.md)
- MR/PR 본문: [`issueops-create-pr`](../issueops-create-pr/SKILL.md) — 리뷰어용이고 형식이 다르다
- 이슈 본문: [`issueops-create-issue`](../issueops-create-issue/SKILL.md)
- 한국어 문장 다듬기: [`fluent-korean`](../fluent-korean/SKILL.md)

## 왜 필요한가

사이클은 단계·lease·봉인·게이트로 굴러가고, 그 기록이 에이전트의 작업 기억에 그대로
남는다. 그걸 그대로 보고하면 **장부를 읽어 주는 것**이 된다. 요청자는 장부를 읽으려고
작업을 맡긴 것이 아니다. 무엇이 참이 되었고 자기가 무엇을 해야 하는지를 알려고 맡겼다.

판별은 간단하다. 보고에서 **읽는 사람의 다음 행동을 바꾸지 않는 문장**을 지운다.
남은 것이 보고다.

## 읽는 사람을 먼저 정한다

| 상대 | 아는 것 | 보고의 초점 |
|---|---|---|
| 작업을 요청한 사람 (기본값) | 문제는 안다. 코드는 안 본다 | 무엇이 해결됐고 자기가 뭘 결정해야 하나 |
| 같은 저장소의 동료 | 코드베이스는 안다. 이 작업은 모른다 | 어디를 건드렸고 자기 작업에 닿는가 |
| 다른 팀 (이 작업을 의뢰한 쪽) | 자기 쪽 맥락만 안다 | 요청이 어떻게 반영됐고 회신할 것이 있나 |

상대를 모르면 기본값으로 쓴다. 상대에 따라 **분량이 아니라 어휘와 초점**이 바뀐다.

## 여섯 규칙

### 1. 첫 줄이 결과다

한 문장으로 "무엇을 만들었고 지금 어떤 상태인가". 서론·범위 선언·진행 과정 없이 시작한다.

- 나쁨: `#2954 사이클을 완주했습니다. 구현·정리·문서·검증 단계를 거쳐…`
- 좋음: `챗 응답에 러시아어 같은 엉뚱한 글자가 섞여 나오는 걸 고치는 기능을 만들어서 MR 올렸고, 스위치는 다 꺼둔 상태입니다.`

### 2. 문제는 증상으로 보여준다

추상적 설명 대신 **실제로 깨진 것을 그대로 붙인다.** 읽는 사람이 "아 저거" 하고
알아보는 순간이 이해의 시작이고, 그 뒤 설명은 전부 그 위에 얹힌다.

- 나쁨: `다국어 응답에서 이종 문자 체계의 토큰이 혼입되는 현상`
- 좋음: `골목을 빠져нага려고 했다` → `원래는 빠져나가려고`

증상을 못 보여주면 그 작업을 아직 요청자의 말로 이해하지 못한 것이다.

### 3. 한 일은 번호 목록으로, 궁금한 순서대로

파일이나 커밋 순서가 아니라 **읽는 사람의 질문 순서**다. 보통 "뭘 만들었나 →
어디에 붙였나 → 지금 켜져 있나" 순이다. 항목마다 한두 문장.

### 4. 지금 상태와 상대가 할 일을 분리한다

`## 지금 상태`에는 클릭할 링크와 사실만, `## 무엇을 하시면 되나`에는 상대의 행동만
적는다. 둘을 섞으면 읽는 사람이 자기 몫을 못 찾는다. 할 일이 없으면 없다고 쓴다.

### 5. 세부는 링크로 미루고, 지금 안 읽어도 된다고 말한다

운영 문서·점검표·실행 기록은 링크 한 줄로 보내고 **언제 읽으면 되는지**를 적는다.
`지금 읽으실 필요는 없고, 켜기로 결정할 때 보시면 됩니다.`

### 6. 놀랄 만한 것은 딱 하나만 미리 말한다

읽는 사람이 나중에 알면 배신감을 느낄 사실 **하나**를 고른다. 둘 이상이면 목록이
되고 목록은 안 읽힌다. 나머지는 5번의 링크로 간다.

고르는 기준은 "나중에 이걸 알았을 때 나를 원망할 것인가"다. 플래그로 안 꺼지는 코드,
되돌릴 수 없는 저장 변경, 남의 작업과 겹치는 파일이 그런 것이다.

## 쓰지 않는 말

사이클의 장부 용어는 보고에 나오지 않는다.

| 쓰지 않음 | 대신 |
|---|---|
| phase, stage, lease, generation | (지운다. 상태는 "MR 올렸고 리뷰 대기"로 충분하다) |
| fingerprint, digest, 봉인, seal | "변경 전과 결과가 같은지 비교해서 테스트로 박아뒀습니다" |
| 게이트, 원장, readiness, record | "확인 항목 전부 통과했습니다" |
| ai-slop-clean, devils-advocate, 적대 리뷰 N라운드 | "리뷰에서 결함 N건 나와서 고쳤습니다" (라운드 수는 결정을 안 바꾼다) |
| worktree, reconcile, actor, actor flags | (지운다) |
| 함수명·파일 경로 | 읽는 사람이 열어볼 것이 아니면 지운다 |

**허용**: 읽는 사람이 실제로 클릭하거나 타이핑할 것. MR/PR 번호와 URL, 그가 직접 켤
환경 변수 이름, 문서 링크가 그렇다.

**숫자**: 읽는 사람의 결정을 바꿀 때만 쓴다. `테스트 5,999개 통과`는 결정을 바꾸지
않는다. `켜면 응답 879건이 바뀝니다`는 바꾼다. 지나온 과정의 수량(커밋 수, 라운드 수,
스위트 수)은 결정을 바꾸지 않으므로 기본적으로 뺀다.

**검증**: 통째로 빼지 않는다. 신뢰의 근거이기 때문이다. 다만 **한 문장**으로, 무엇을
어떻게 확신하는지만 적는다. `원본 파이썬과 우리 코드에 같은 문장 6,000개를 넣어
결과가 한 글자도 다르지 않은지 비교했고 차이 0건입니다.`

## 사실은 기록에서 읽는다

보고에 들어가는 값은 지어내지 않는다. 확인하지 못한 줄은 빼거나 `미확인`으로 적는다.

```bash
issueops status --id "$ISSUEOPS_ID" --json
issueops next --id "$ISSUEOPS_ID" --json
```

| 보고에 쓰는 것 | 출처 |
|---|---|
| 무엇을 만들었나 | intent contract의 해석과 성공 기준 |
| 증상 예시 | 이슈 본문, 전달 명세, 테스트의 실제 입력 |
| 어디에 붙였나 | 실제 변경 파일과 계획의 투입 지점 |
| 지금 켜져 있나 | 설정 파일의 실제 값 (추정하지 않는다) |
| MR/PR 링크 | 봉인된 remote artifact |
| 놀랄 만한 것 | 실행 기록의 "계획에서 벗어난 점"과 리뷰가 남긴 비차단 관찰 |

## 형태

```markdown
## 한 줄
<무엇을 만들었고 지금 어떤 상태인가. 한 문장>

## 무슨 문제였나
<증상 2~3개를 실제 텍스트로. 그리고 누가 왜 요청했는지 한 문단>

## 뭘 했나
1. <만든 것. 어떻게 맞다고 확신하는지 한 문장>
2. <어디에 붙였는지>
3. <지금 켜져 있는지>

## 지금 상태
<MR/PR 링크와 사실>

## 무엇을 하시면 되나
<상대의 행동. 없으면 없다고 쓴다>

## 나중에 볼 것
<문서 링크 한 줄 + 언제 읽으면 되는지>

<놀랄 만한 것 하나. 왜 그런지와 그래서 무엇을 했는지>
```

절 제목은 상황에 맞게 바꾼다. **순서는 바꾸지 않는다** — 결과, 문제, 한 일, 상태,
상대의 행동 순이 읽는 사람의 질문 순서다.

분량은 스크롤 한 번이다. 넘치면 내용을 줄이는 것이 아니라 링크로 뺀다.

## 되물어 오면

`뭔 소린지 모르겠다`는 분량이 아니라 **어휘와 초점**의 문제인 경우가 대부분이다.
같은 내용을 짧게 다시 쓰지 말고, 위 「쓰지 않는 말」을 다시 걸러 낸 뒤 증상 예시부터
새로 시작한다. 한 번 설명이 통했으면 그 뒤로는 같은 어휘를 유지한다.

되물음이 특정 문장을 가리키면 그 문장만 푼다. 보고 전체를 다시 쓰지 않는다.

## 나쁜 예

| 나쁜 행동 | 문제 |
|---|---|
| 단계 전이를 순서대로 나열한다 | 장부를 읽어 준 것이다. 읽는 사람의 행동이 하나도 안 바뀐다 |
| 리뷰 라운드와 결함 번호를 그대로 옮긴다 | 내부 사건 기록이다. 결함이 있었고 고쳤다는 사실만 남긴다 |
| 통과한 테스트 수·커밋 수를 앞에 둔다 | 분량 증명이지 결과가 아니다 |
| 증상 없이 "이종 문자 혼입을 교정한다"로 시작한다 | 읽는 사람이 자기 문제로 알아보지 못한다 |
| 놀랄 만한 것을 다섯 개 나열한다 | 목록이 되면 안 읽힌다. 하나만 고른다 |
| 확인하지 않은 값을 그럴듯하게 적는다 | 보고가 기록과 어긋난다. 모르면 `미확인` |
| 상대가 할 일을 상태 설명 안에 섞는다 | 자기 몫을 못 찾는다 |
| 이 형식으로 MR 본문을 쓴다 | MR은 코드를 볼 리뷰어용이고 형식이 따로 있다 |
| `쉽게 설명해줘`에 같은 내용을 짧게만 다시 쓴다 | 어휘를 안 바꾸면 두 번째도 안 통한다 |

## 검증

- 보고에서 「쓰지 않는 말」 표의 왼쪽 열이 하나도 안 나온다.
- 모든 문장이 읽는 사람의 다음 행동이나 판단을 바꾼다.
- 증상 예시가 실제 입력에서 나온 것이고 지어낸 것이 아니다.
- 링크와 번호가 기록의 값과 같다.
