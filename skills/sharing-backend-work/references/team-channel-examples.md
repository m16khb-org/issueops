### A-1. `[API]` 응답·에러 추가

```
{서브팀 멘션}
아래 내용 문제없을지 확인해주시면 감사드리겠습니다.

*{대상 기능} API에 {status} 응답이 새로 추가됩니다 (#{이슈})*

{계기 한 줄}. *기존에 {이전 status}으로 내려가던 케이스가 {새 status}로 바뀝니다.*
{클라이언트가 할 일 한 줄}.

*1. 대상 엔드포인트*
• {METHOD} /{경로}

*2. 신규 응답*
• HTTP status {status}
• code {CODE}
• message {유저에게 그대로 노출 가능한 문구}

*3. 같은 값으로 판정되는 차이*
• {정규화되어 병합되는 입력}

*4. 다른 값으로 판정되는 차이*
• {병합되지 않는 입력}

*5. 저장 규칙 (신규)*
• {서버가 값을 어떻게 바꿔 저장하는지}

*6. 기존 동작과의 차이*
• 이전: {동작} → 유저는 {결과}
• 이후: {동작}

*7. 함께 바뀌는 동작 (에러 아님, 참고용)*
• {클라이언트가 알아야 할 부수 변화}

상세: {이슈 링크}
```

3~5번은 서버가 값을 정규화할 때만 씁니다. 7번은 각 플랫폼이 자기 처리 방식을 정하는 재료입니다.

**예시** — 태그 중복 시 409 추가

```
@web @ios @aos
아래 내용 문제없을지 확인해주시면 감사드리겠습니다.

*컬렉션 생성/수정 API에 409 응답이 새로 추가됩니다 (#1234)*

태그 중복으로 컬렉션 생성이 실패하던 이슈(#1234)를 수정하면서,
*기존에 500으로 내려가던 케이스가 409로 바뀝니다.* 앱에서 409 핸들링 확인
부탁드립니다. 태그 저장 규칙도 함께 정리되어 아래 5번을 같이 봐주세요.

*1. 대상 엔드포인트*
• POST /collections
• PUT /collections/:collectionId
• PUT /collections/:collectionId/v2

*2. 신규 응답*
• HTTP status 409 Conflict
• code DUPLICATE_TAG
• message 중복된 태그가 있습니다. 중복된 태그를 제거한 뒤 다시 시도해 주세요.

*3. 같은 태그로 판정되는 차이*
• 대소문자 — Home = home
• 전각/반각 — ユリカ = ﾕﾘｶ
• 히라가나/가타카나 — ゆりか = ユリカ
• 앞뒤 공백 — 오수 = 오수

*4. 다른 태그로 판정되는 차이*
• 악센트 — cafe ≠ café
• 중간 공백 — 말투 예시 ≠ 말투예시

*5. 태그 저장 규칙 (신규)*
• 태그는 앞뒤 공백이 제거된 상태로 저장됩니다.
• 공백만 있는 태그는 저장되지 않습니다. 요청은 실패하지 않고 해당
  태그만 조용히 제외됩니다.
• 이미 저장된 기존 태그는 이번 변경으로 소급 수정되지 않습니다.

*6. 기존 동작과의 차이*
• 이전: 3번에 해당하는 태그가 함께 들어오면 트랜잭션 전체가 롤백되며
  500 (알 수 없는 오류) → 유저는 원인을 알 수 없었음
• 이후: 서버가 대부분을 자동 병합해 정상 처리하고, 그래도 남는 극히
  예외적인 케이스만 409로 안내

*7. 함께 바뀌는 동작 (에러 아님, 참고용)*
동일 판정되는 태그를 여러 개 입력하면 서버가 먼저 들어온 원문 하나로
병합해서 저장합니다.
• 예: 기존에 Home이 저장된 상태에서 home을 추가 → Home에 연결
• 따라서 조회 응답에는 입력한 home이 아니라 Home이 내려갑니다
• 트리거 매칭도 저장된 원문(Home) 기준이라, 소문자 home만 등장하면
  해당 규칙은 걸리지 않습니다
```

이런 글의 7번이 스레드를 만들어 냅니다. 실제로 이 형태의 공지에서 iOS는 `message` 필드 타입과
다국어 지원 여부를, Android는 기존 데이터에 이미 중복이 있는지를 되물었고, 결론은 각 클라이언트가
`code`로 분기해 자체 문구를 띄우는 것으로 정리됐습니다. `statusCode + code` 조합으로 매칭하고
그 외에는 statusCode만 보는 공통 처리 방침도 그 스레드에서 나왔습니다.

### A-2. `[API]` 스펙 변경 묶음

클라이언트용과 어드민용을 두 글로 나눠 각각 다른 이슈를 답니다.

```
[{과제명}] {계기} — {클라이언트|ADMIN} API 스펙 변경 공유 (상세: #{이슈})

• {필드 또는 엔드포인트}: {이전} → {이후} — {부연}. {하위 호환 여부}
• {신설}: {METHOD} {경로} — {교체 방식이나 제약}
• {보류 항목}: {보류 사유}

상세 스펙은 기존에 공유드렸던 문서에 반영해놨습니다!
{이슈 링크}
{담당자 멘션}
```

**예시** — 구독 상품 개편

```
[구독 상품 개편] 회의 반영 — 클라이언트 API 스펙 변경 공유 (상세: #1201)

• benefits 응답 구조 변경: 객체 → 배열 [{ key, value, displayName }] —
  displayName은 유저 언어로 서버가 현지화해서 내려감 (카탈로그 · 확인 ·
  내 구독 · 결제이력 4곳 공통)
• promotionPrice 제거 (페이즈2 보류): 페이즈1 응답에서 미노출,
  표시 가격은 price 그대로 사용
• 팝업 시그널 type 신설: 스트림 응답의 popup.type = UPSELL / PURCHASE.
  구버전 클라는 type 무시해도 기존 동작 그대로 (하위 호환)
• PURCHASE는 web 전용: 페이즈1은 웹 결제만 지원 → 비-web 플랫폼은
  항상 UPSELL
• (테스트용) 스트림 body에 delayTime 추가: admin 계정 한정 청크 딜레이
  오버라이드(ms), QA용 — 일반 유저가 보내면 무시됨

상세 스펙은 기존에 공유드렸던 문서에 반영해놨습니다!
{이슈 링크}
{담당자 멘션}
```

같은 과제의 ADMIN 쪽은 **별도 이슈를 달고 따로 게시**합니다. 항목마다 하위 호환 여부와 플랫폼
제약이 붙고, 보류한 항목도 사유와 함께 남습니다. 적지 않으면 다음 회의에서 같은 논의를 다시 합니다.

### A-3. `[API]` 파라미터·필드 추가

```
{배경 한 줄}
{서브팀 멘션}
• {영향받는 화면}
    ◦ {화면 링크}

API 변경사항
1. {METHOD} {경로} 에 {파라미터} 쿼리 파라미터 추가
    ◦ {형식과 예시}
    ◦ 미전달 시 기존과 동일하게 동작 (하위 호환)
2. 응답 항목에 {필드} 추가
    ◦ 예: {값 예시} 또는 null ({null이 되는 조건})

• {화면에 필요한 UI 작업}
    ◦ default : {미선택 기본 동작}
    ◦ {선택 시 호출 형태}
```

**예시** — Export 화면 언어 필터

```
운영팀에서 다국어 데이터에 대해서도 다운로드를 요청하여 아래의 API에
Filter 추가 개발 부탁드립니다..!
@backend
• AdminPage
    ◦ {어드민 화면 링크}

API 변경사항
1. GET /admin/exports API에 languageCodes 쿼리 파라미터 추가
    ◦ 쉼표 구분 문자열 (예: ko,ja)
    ◦ 미전달 시 기존과 동일하게 동작 (하위 호환)
2. 응답 항목에 languageCode 필드 추가
    ◦ 예: "languageCode": "ko" 또는 null (기존 경로 데이터)

• Export 리스트 화면에 언어 코드 필터 UI 활성화
    ◦ default : 미선택 기능 지원 (기존 데이터)
        ▪︎ languageCodes 보내지않음
    ◦ 멀티 셀렉트 기능 지원
        ▪︎ 선택된 값을 ?languageCodes=ko,ja 형태로 API 호출
• 리스트 테이블에 언어 코드 컬럼 표시
    ◦ 응답의 languageCode 필드 (없으면 - 또는 빈칸)
```

쿼리 파라미터는 복수형(`languageCodes`), 응답 필드는 단수형(`languageCode`)입니다.
이름이 갈리면 반드시 양쪽을 다 적습니다. 개발을 요청하는 글도 계약을 먼저 적고 UI 작업을 뒤에 붙입니다.

### A-4. `[공지]` 환경·엔드포인트

```
{무엇이 바뀌는지} 공유드립니다

• {새 주소 또는 작업 내용}
    ◦ {접근 조건}
    ◦ {접근 조건}

{왜 바뀌었는지 또는 예상되는 증상}
Client 대응 사항은 {없습니다 | 아래와 같습니다}.
```

**예시** — DEV 스웨거 주소 변경

```
DEV 환경 스웨거 링크가 아래의 주소로 다시 롤백 되었습니다!
• {DEV Swagger 주소}
    ◦ VPN 사용해서 접근 가능
    ◦ 회사 WIFI 로 접근 가능 (무선)
    ◦ 회사 LAN 으로 접근 가능 (유선)
    ◦ LTE 등 외부 인터넷 접속 불가

VPN을 키지않고 회사 WIFI로 접속가능하게 하기위해서 다시 Swagger Doc
경로가 다시 변경되었습니다. 문서 경로가 계속 바뀐점 양해 부탁드립니다
```

접근 조건은 되는 경로와 안 되는 경로를 모두 적습니다.
`LTE 등 외부 인터넷 접속 불가` 한 줄이 "집에서 왜 안 되나요" 문의를 없앱니다.

### A-5. `[배포]` 완료

```
[배포] {버전} {대상 서비스} · {대상 환경} — 완료

{무엇이 나갔는지 한 줄}

*포함*
• {기능 또는 수정}

*영향*
• 무중단 여부: {무중단 | 재기동 N초 | 마이그레이션 포함}
• 롤백: {방법 한 줄}

MR: {링크}
```

실제로 올라오는 배포 글은 `{버전} prod api 배포 완료했습니다.` 한 줄입니다.
무중단 여부와 롤백 방법 두 줄이 없으면 문제가 났을 때 글쓴 사람을 찾아야 합니다.
A 유형 중 배포 완료만 MR 링크를 답니다.

### A-6. `[요청]` 타 파트 확인·협의

```
{서브팀 멘션}

안녕하세요, {주제} 관련해서 협의드리고 싶은 내용이 있습니다.

{현재 구조가 어떻게 동작하는지}. {그래서 무엇이 막히는지}.

{지금 표면화된 계기와 그대로 두면 커지는 위험}.

요청 사항
• {행동}
    ◦ {제약 조건}
• (확인 필요) {결정이 필요한 선택지}

cc. {관련 서브팀}
```

**예시** — 심사 모드 데이터 전환 구조

```
@backend

안녕하세요, 심사 모드 데이터 전환 구조 관련해서 협의드리고 싶은 내용이
있습니다.

현재는 앱이 GET /review-mode로 심사 여부를 받아서, 그 값을 목록 API
쿼리파라미터로 다시 서버에 전달하는 구조입니다. 이 방식은 해당 파라미터
계약이 있는 API에서만 전환이 가능해서, 조회 API가 늘어날 때마다 계약을
추가해야 하는 확장성 문제가 있습니다.

이 문제가 지금 당장 표면화된 계기가 있는데, 홈화면 개편으로 목록 API
하나만 전환 대상에 반영되고 나머지 탭은 반영되지 않고 있는 상태입니다.
여기에 웹으로 전환한 뒤 심사 요청까지 들어가면, 심사용 데이터가 반영되지
않은 화면이 그대로 노출되는 문제가 더 커질 수 있습니다.

요청 사항
• 어드민에서 심사 상태를 켜고 끄면, 조회 API가 서버에서 직접 판정해
  심사용/실데이터를 전환
    ◦ 웹 서비스에는 영향이 없어야하므로 헤더값의 스토어, 버전, 플랫폼
      정보 활용하여 반영필요
• (확인 필요) 헤더 분기 vs 파라미터 계약 확장 — 어느 쪽으로 갈지

cc. {관련 서브팀}
```

협의를 요청하는 글에서는 짧은 인사 한 줄까지가 팀 관행입니다.
결정이 필요한 항목이 있으면 요청 사항 안에 `(확인 필요)`를 붙여 행동과 구분합니다.
이 줄이 없으면 그 결정이 본문이 아니라 스레드에서 이뤄집니다.
