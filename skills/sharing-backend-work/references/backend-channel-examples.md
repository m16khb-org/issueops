### B-2. `[분석]` 조사 결과

```
[분석] {제목} · {대상}

결론부터 말씀드리면 {판단 한 줄}.

*무엇을 / 왜*
• {사실 + 수치 이전 → 이후}
• {코드 근거 path/file.ts:줄번호}
• {반증하거나 배제한 가설}

*영향*
• {지금 나타나는 모습}
• {바뀌지 않은 것}

*조치 / 다음*
• {할 일 — 담당자, 기한} 또는 추가 조치 필요 없음

*확인이 필요한 부분*
• {미결 질문 — 없으면 섹션 삭제}

이슈: · MR: · 런북:
```

**예시** — 자체 서빙 모델 폴백 원인

```
[분석] 자체 서빙 모델 폴백 원인 · prod

결론부터 말씀드리면 평상시 폴백률은 사실상 0이고, 누적 수치가 높아 보인 건
특정일 GPU 서버 장애 스파이크가 섞였기 때문입니다.

*무엇을 / 왜*
• 원인은 TCP connect timeout 이 아니라 연결 수립 후의 read ECONNRESET
• 평상시 폴백률 0.006% 수준
• 누적 0.28% — 장애 구간 포함
• 서비스 메시 egress 연결 수립 실패 0건, 비정상 종료 비율이
  DB 폴백 비율과 일치

*영향*
• 대화 실패로 이어진 건은 없습니다
• 누적 대시보드 수치는 장애 구간을 제외하고 보셔야 합니다

*조치 / 다음*
• 추가 조치 필요 없음

런북: {Canvas 링크}
```

원문도 이미 결론을 먼저 씁니다. 양식이 더하는 것은 **섹션 이름의 고정**뿐입니다.
한 문단에 뭉쳐 있던 사실이 `무엇을 / 왜`와 `영향`으로 갈리면, 읽는 쪽이
"나한테 뭘 시키는 글인가"를 세 번째 섹션에서 바로 확인합니다.

### B-3. `[변경]` 설정 반영

```
[변경] {무엇을 바꿨는지} · {대상} ({반영 시각})

{왜 바꿨고 결과가 어떻게 됐는지 한 줄}.

*바꾼 것*
• {항목}: {이전} → {이후}

*개발팀에서 알아두시면 좋을 내용*
• {달라지는 화면·지표·동작}
• {달라지지 않는 것}

*반영 중 발생한 데이터 공백*
• {공백 구간과 범위}
• {앞으로 예상되는 알람}

*조치 / 다음*
• {후속 작업 — 담당자, 기한}

이슈: · MR: · 런북:
```

**예시** — 메트릭 수집 설정 조정

```
[변경] Prometheus 메트릭 수집 설정 · prod (16:05 반영)

TSDB 용량 알람에 대응해 PVC 증설 대신 사용처 없는 메트릭을 걸러냈고,
저장 샘플이 절반 이하로 줄었습니다.

*바꾼 것*
• 저장 샘플: 약 16K/s → 7K/s
• API 지연 히스토그램 버킷: 34개 → 14개
• 컨테이너 CPU 수집 간격: 10초 → 30초
• 참조처 없는 프록시 메트릭 148종 제거

*개발팀에서 알아두시면 좋을 내용*
• 1~5초 구간 p95·p99 가 덜 정밀합니다.
  1초 경계는 그대로라 "1초 초과" 판정은 동일
• HPA 는 metrics-server 기반이라 변화 없음

*반영 중 발생한 데이터 공백*
• 16:05~16:13 API 지연 데이터 공백 (로그·Loki 전송은 정상)
• 블록 만료까지 용량 알람이 며칠 더 발생

*조치 / 다음*
• 추가 조치 필요 없음 (블록 만료 시 자동 해소)

이슈: · MR: · 런북:
```

이 글이 **바뀐 것과 바뀌지 않은 것을 함께** 적는 본보기입니다.
"HPA는 metrics-server 기반이라 달라지지 않습니다"가 "버킷을 34개에서 14개로 줄였습니다"보다
읽는 쪽에 더 중요합니다.

### B-4. `[장애]` 사후 정리

진행 중인 상태 갱신은 스레드로 하고, 복구 후 정리본을 이 채널에 남깁니다.

```
[장애] {현상} · {대상} — {조사 중 | 복구됨}

{무엇이 언제부터 언제까지, 사용자 영향은}

*타임라인* (KST)
• HH:MM 발생 — {징후}
• HH:MM 인지 — {알람 또는 제보 경로}
• HH:MM 복구 — {조치}

*원인*
• {직접 원인}
• {왜 그전까지 안 잡혔는지}

*사용자 영향*
• {실패 건수·비율, 없으면 "없었습니다"}

*재발 방지*
• {조치 — 담당자, 기한}

이슈: · 런북:
```

**예시** — 인증서 만료로 인한 전량 폴백

```
[장애] 자체 서빙 모델 전량 폴백 · prod — 복구됨

TLS 인증서 만료로 21분간 요청이 전량 폴백됐습니다.
폴백이 정상 동작해 대화 실패는 없었습니다.

*타임라인* (KST)
• 11:06:58 발생 — 추론 게이트웨이 인증서 만료
• 11:28:15 복구 — 인증서 재발급 및 반영

*원인*
• certbot 자동 갱신이 한 달 전부터 계속 실패
• 방화벽에 80 포트 허용 규칙이 없어
  Let's Encrypt HTTP-01 검증이 차단됨

*사용자 영향*
• 대화 실패 0건 (전량 폴백 제공자로 우회)

*재발 방지*
• 80 포트 허용 규칙 추가, 자동 갱신 정상화 완료
• 외부 인증서 만료 알람 추가 ({담당자}, {기한})

런북: {Canvas 링크}
```

`사용자 영향`은 "없었습니다"라도 반드시 적습니다. 비워두면 읽는 사람이 영향 범위를 되묻습니다.
