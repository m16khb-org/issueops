# 한 사건, 세 청중

[전체 템플릿](case-templates.md) · [공통 작성 규칙](../SKILL.md)

연결 풀 고갈로 서비스가 재시작되고 응답이 지연된 사건을 같은 사실에서 세 갈래로 씁니다.

**A. `{전사 채널}`** — 클라이언트가 무엇을 겪었고 무엇을 해야 하는지만 남깁니다.

```
[공지] 채팅 응답 지연 · 14:20~14:41 — 복구됨

21분간 채팅 응답이 느려졌습니다. 대화 실패는 0건이고 응답 지연만 발생했습니다.

*영향*
• 응답 p99 지연 1.2초 → 8.4초, 14:41 정상화
• 클라이언트 재시도로 흡수되어 유저에게 실패로 보이지 않았습니다

Client 대응 사항은 없습니다!
```

**B. `{백엔드 채널}`** — 동료가 검증하고 이어받을 수 있게 씁니다.

```
[분석] chat-api Redis 연결 풀 고갈 · prod

결론부터 말씀드리면 maxPoolSize 하드코딩이 원인이고, 50으로 올려 복구했습니다.
근본 조치는 남아 있습니다.

*무엇을 / 왜*
• 14:20~14:41 파드 3회 재시작, 응답 p99 1.2s → 8.4s
• apps/chat-api/src/config/redis.config.ts:48 의 maxPoolSize 가 10 고정
• 노드 CPU 40%, 네트워크 정상, Redis maxclients 여유 충분

*영향*
• 대화 실패 0건, 응답 지연만 발생
• 14:41 이후 지표 정상

*조치 / 다음*
• maxPoolSize 10 → 50 ({MR} 머지, 14:41 반영)
• 근본 조치 미결 — 담당자·기한 미정

이슈: · MR:
```

**C. 리드** — 리드가 방향만 고르면 되게 씁니다.

```
결론: Redis 연결 풀 크기가 코드에 고정돼 있어 트래픽 증가를 못 따라간 건입니다.
임시 조치로 복구했고, 근본 조치는 환경변수 분리를 권장합니다.

### 증거 체인
1. 파드 이벤트: 14:20~14:41 chat-api 3회 재시작
2. 지표: 같은 구간 응답 p99 1.2s → 8.4s, 14:41 이후 원복
3. 코드: apps/chat-api/src/config/redis.config.ts:48 maxPoolSize = 10 고정

### 배제된 것
- 노드 리소스: CPU 40%로 여유
- 네트워크: 이상 없음
- Redis 서버측: maxclients 여유 충분

### 해석
- 풀 크기가 코드 상수라 트래픽이 늘면 같은 방식으로 재발합니다.
- 서비스 영향: 대화 실패 0건, 응답 지연만 발생했습니다.

### 권장 대응
1. 풀 크기를 환경변수로 분리 — 권장. 재배포 없이 조정 가능해집니다.
2. 연결 풀 사용률 알람 신설 — 1번과 함께 하면 재발을 사전에 잡습니다.

조사 중 쓰기 작업은 maxPoolSize 변경 배포뿐입니다.
```

세 글의 차이가 요점입니다. A에는 코드 경로와 MR 번호가 없고, B에는 증거 체인과 권장 순위가 없으며,
C에는 클라이언트 대응 문구가 없습니다.
