# Pipeline skill routing: companion skills called by name, base drift as a three-surface model, frontend as a next flag

- Date: 2026-09-08
- Kind: `adr`
- Source: cli
- Summary: Every companion skill the router table promises is now called by name in its stage body, base drift is observable through three surfaces with distinct stage roles, and a frontend flag routes UI work to ui-ux-craft and browser QA.
- Context: A reference-graph audit of all 51 skills found two gaps. First, the router table promised companions that no stage body ever called: implementation-planning and web-research at stage 1, design-review, database-design and prompt-engineering at stage 3, issueops-debugging and code-quality-metrics at stage 4. An agent follows the stage body, not the table, so those skills were unreachable. Second, four skills sat outside the pipeline entirely: review-agent-feedback duplicated by prose in references/review-feedback.md, rebase-onto-parent whose sync-base route nothing pointed at, ui-ux-craft and the aside QA skills with no frontend trigger, and requirements-analysis with no document-input trigger. Separately, upstream_synced measures the feature branch against its own upstream, so a base branch that advanced was invisible to every surface.
- Decision: (1) Align the table with the bodies: stage 3 names issueops-review because that is how design-review is actually invoked, stage 4 drops code-quality-metrics because the before/after measurement belongs to stage 5, and each body gains a concrete trigger sentence. The debugging route is tied to verified-execution's three-failure counter so one loop has one cap. (2) references/review-feedback.md delegates bot threads to review-agent-feedback and keeps the human-reviewer reply and options formats, which that skill places outside its own scope. (3) Base drift becomes a three-surface model with distinct stage roles: strict readiness emits a base_advanced warning without fetching, which next now forwards as a stage 5-8 hint; execution sync-base --preview fetches and is the truth, run at the implement start gate after the claim and again read-only at verify; --apply is allowed only at implement entry, before any seal exists, and the skill documents that it pulls the base's files into this cycle's change set because diffBaseRef keeps the sealed BaseSHA. (4) next.review gains a frontend bool computed from the paths already observed for the tier; it routes stage 4 to ui-ux-craft and stage 7 to aside-web-qa with all four aside inputs mapped to cycle artifacts. (5) requirements-analysis handles document inputs at stage 1 and prompt-engineering handles LLM-facing prompt bodies at stage 3.
- Consequences: Two new next.review and readiness fields join the contract surface; strict readiness performs two more local git reads from any stage that runs it, and stages 5-8 next output now also shows the branch-mismatch and source_misdirect warnings readiness already produced. Rejected: making base drift a blocking key, which would change PR gate policy; mapping upstream_synced to sync-base, whose meaning differs; applying a base sync during verify, which would invalidate the ai-slop-clean, implementation-review and project-docs-review seals at once and re-enter stage 5; a Signals slice for a single value; changing diffBaseRef's seal semantics so the change set follows a moving base, deferred to its own decision; extending the owner prompt's required-skills list, since the router already reaches stage skills.
