# opencode v2 as the fifth first-party host

- Date: 2026-10-18
- Kind: `adr`
- Source: issueops cycle io-7426b49dc042 (#568)
- Summary: opencode 2.0.32 is the fifth first-party host (codex, claude, omo, omp, opencode; installers end with agy), and only a --standalone session, proven by its own `opencode serve --stdio` process, can own an IssueOps lease.
- Context: opencode v2 runs every session's shell tools under one shared background service (`opencode serve --service`, detached by the first client) unless the client is started with `--standalone`, which spawns a private `serve --stdio` child that dies with the client even on SIGKILL. While the client that started the shared service is alive, the shell ancestry (shell -> serve -> opencode TUI) looks the same as a standalone one by executable names, so an omp-style nearest-ancestor receipt cannot tell a per-session server from the shared one. opencode exports OPENCODE_SESSION_ID to every agent shell (the child session id inside a subagent), has no session-start or compacted event, and runs `ctx.session.hook("context")` before every agent-loop model call, including the first one after a compaction. Its user config is `$XDG_CONFIG_HOME/opencode` (else `~/.config/opencode`): `opencode.json` and `opencode.jsonc` are both loaded, the jsonc wins, and a same-named `mcp.servers` entry is replaced whole.
- Decision: Add opencode after omp everywhere (`codex, claude, omo, omp, opencode`; installers `..., opencode, agy`). Install writes user scope only: skill links in `<config>/opencode/skills`, the `issueops` entry under `mcp.servers` of `<config>/opencode/opencode.json` (HTTP `type: remote` with bearer and catalog digest header and `oauth: false`, or stdio `type: local` with the catalog digest in `environment`; `codemode: false` in both; the file is written 0600 and narrowed to 0600 for HTTP), and `<config>/opencode/plugins/issueops.js`. `opencode.jsonc` is read, never written: an `mcp.servers.issueops` there fails the install, an unreadable file only warns. An `opencode.json` that already holds comments or trailing commas, which opencode accepts, fails the opencode install with its path instead of being rewritten as plain JSON. `--project-local` writes `.opencode/opencode.json` (stdio) or removes its `issueops_project` entry (HTTP). Activation reads back the MCP entry by meaning and the plugin by bytes; native activation now requires eleven surfaces. The plugin registers only the `context` session hook: it runs `issueops hook session-start` (root) or `hook subagent-start` with the agent type (child, found through one `ctx.session.get`) once per session with a 10 second limit, caches the result for up to 512 sessions, and appends the catalog to every model call; it never writes process.env. The native actor reads OPENCODE_SESSION_ID; an omp or other host id beside it is ambiguous and fails closed. The receipt rule lives in core: `NormalizeNativeActor` requires an opencode-named receipt for host `opencode`, and `verifyNative` accepts any opencode-named receipt, whatever host was declared, only when the live argv (read with the start identity re-checked, never stored) has `serve` right after the first opencode token and `--stdio` after it. Interactive launch is `[/usr/bin/env OPENCODE_CONFIG_CONTENT={"model":M}] opencode --standalone --auto [extra] --prompt P` without effort, worktree relaunch is `cd <worktree> && opencode --standalone`, and print argv is `opencode run --standalone --model M[#E]` with the prompt on stdin. Role models gain an `opencode` settings section; opencode effort is a model-defined variant, so docs-only lowering and review escalation never change it. `trace analyze --input-format opencode-json` sums `step_finish` tokens (output plus reasoning). The opt-in host probe runs a private `opencode serve` with a random password and private HOME/XDG roots, waits for `/api/info`, warms the episode location until the probe MCP server is `connected`, runs `opencode run --server` with tools other than the probe denied, and lets a guard plugin block the probe tool unless the catalog reached the request.
- Consequences: A shared-service opencode session cannot claim, prepare, mutate, or `mcp authorize`; over HTTP its workspace MCP tools fail with `authority_required` while server-scope tools and argument-free `harness_inspect` work, and over stdio the MCP process has no OPENCODE_SESSION_ID so `issueops_execution` mutations fail. A receipt path whose earlier piece also ends in `opencode` fails closed. The first model request of a cold `--standalone` session can lack MCP tools because the location connects MCP lazily. The interactive TUI keeps the variant from the user's `model.json`, so the effort that prepare reports may differ. The JSON stream omits the last step's `step_finish`, so trace sums undercount. opencode's free Zen models answer probe episodes with `provider.auth` 403 ("free tier can only be used from within OpenCode"), reported as `harness_environment:provider_auth_failed`; a probe needs a keyed provider model, whose `*_API_KEY` variables are the only user variables passed in. cmux was not available to observe; the launcher argv is pinned by tests only. A cmux handoff to opencode never records `owner_claimed`: the cmux target process is the TUI while the claim receipt is its `serve --stdio` child, so the exact process match cannot hold; the claim itself still succeeds. A user whose `opencode.json` has comments must move them into `opencode.jsonc` or delete them before install or update succeeds. Older binaries reject records with host `opencode` and settings files with an `opencode` section. Existing user installs get opencode only after `issueops update` from the merged source checkout; removing it means deleting `plugins/issueops.js`, `mcp.servers.issueops`, and the skill links.
- Evidence:
  - opencode 2.0.32 binary strings, --help, `opencode api`, and temp HOME/XDG mock-provider runs (Rounds 1-5 of the plan research)
  - internal/domain/issueops/native_actor.go, internal/application/authority/service.go (requireOpencodeStandaloneServer)
  - internal/adapter/opencode, internal/adapter/hostprotocol/opencode.go, internal/adapter/hostprobe/opencode.go
  - ISSUEOPS_OPENCODE_LIVE=1 go test -run TestOpencodeLiveStandaloneSession ./internal/adapter/opencode (real opencode 2.0.32 with a mock provider)
  - ISSUEOPS_TOOL_CONFORMANCE_LIVE=1 issueops contract conformance live --hosts opencode --model opencode=opencode/deepseek-v4.1-flash-free (provider_auth_failed)
- Alternatives / rejected options:
  - Extend extensionhost.Spec with file names, key paths, and entry builders: rejected; two hosts would carry a large abstraction and the omo/omp goldens would churn.
  - Accept the shared service as a receipt: rejected by the user; it outlives sessions, so a dead holder could never be detected.
  - Tell standalone apart by executable and parent names: rejected; a live TUI that started the shared service gives the same chain.
  - Store argv in the receipt DTO: rejected; records and every receipt comparison would change for one check made at verification time.
  - Export the session id from the plugin into process.env like omp: rejected; one server hosts many sessions.
  - Re-inject on a compaction event: rejected; v2 has no such event and the context hook already runs on every call.
  - Rewrite a commented `opencode.json` as plain JSON: rejected; the merge would silently drop the user's comments.
