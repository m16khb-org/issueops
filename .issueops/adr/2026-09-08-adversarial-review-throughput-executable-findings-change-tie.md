# Adversarial review throughput: executable findings, change tiers, and concurrent read-only verification

- Date: 2026-09-08
- Kind: `adr`
- Source: cli
- Summary: Review rounds now hand the caller executable CHECKs and are judged by a delta subagent, the change set picks the review tier and effort, unwaived revise rounds are capped at three, and the verify stage runs its read-only tracks concurrently.
- Context: Adversarial review was the slowest and most expensive part of a cycle, and nothing measured it. Every re-review round re-read the whole target through an LLM even when the correction was mechanical; every diff got the same four lenses and the same planner effort regardless of whether it touched a schema or a markdown file; the three-round limit existed only in skill prose; and the verify stage ran its battery, schema measurement and diff review one after another even though all three are read-only against the same sealed fingerprint. The record already held the raw material for measurement (devils_advocate_review.history, regress_events, phase_ledger) and the codebase already had a conservative change-path classifier (pathIsSchemaChange) that only the schema-evidence gate used.
- Decision: (1) Add issueops review-metrics, a read-only projection over records: rounds, verdict distribution, regress counts, stage durations and round gaps, aggregated per repository. It exists as a command rather than a status field because the inventory ListEntry carries no aggregation fields; the single-id path alone would be derivable from status --json. (2) Move pathIsSchemaChange into the domain and add ChangeTier with docs-only, contract, schema-auth and default, ranked schema-auth > contract > docs-only > default, with auth detection restricted to exact directory segments. (3) Surface tier, lenses and a tiered effort in next.review; only docs-only lowers effort. Classification runs only from the implement phase onward and adds two git reads there; earlier phases never call the port, and an unobservable change set falls back to default with a warning. (4) Cap unwaived devils-advocate revise verdicts at three per plan phase; the error routes through stop then remote reflect-devils-advocate then regress, because regress refuses to run while the current verdict is revise. (5) issueops-review requires CHECK/EXPECT on blocking findings, the caller runs them through verify-work, and a delta subagent decides the verdict; the caller only records it. (6) issueops-verify starts the battery, schema measurement and diff review concurrently on the sealed diff and discards the review verdict if the battery fails.
- Consequences: One new public CLI command and two new next.review fields join the contract surface; the usage golden, command parser, lifecycle catalog and response-contract golden all carry them. A cycle sitting at three unwaived revise verdicts must now record stop or a waiver instead of another revise. next reads git twice more from the implement phase onward. Rejected: splitting the code fingerprint from the doc fingerprint to let docs and verify run concurrently, because the gate judgement would double; a new gates add subcommand, because gates init already accepts repeated --gate and the ledger file is created at stage-4 entry; parallel lens review by default, because coordination cost exceeds the saving outside schema-auth; a parallel-allowed marker in ReviewLensesForTier, because the verify skill sentence already owns that condition; substituting the tier into the owner prompt, because owner artifacts are built at execution prepare when the worktree is empty and the tier is therefore always default.
