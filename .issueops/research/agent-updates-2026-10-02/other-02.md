# GitHub Copilot CLI: releases and extensibility evidence

**Retrieved:** 2026-10-02
**Scope:** One bounded public-source evidence lane for IssueOps performance, optimization, and visibility. No performance measurements are claimed.

## Findings

1. **Current release signal: reliability, policy, and telemetry—not a measured speedup.** The official `github/copilot-cli` releases page lists stable **v1.0.91 (2026-10-01)** and a newer **v1.0.92-0 pre-release** (the fetched listing provides no publication date for that prerelease). v1.0.91 adds sandbox proxy-CA management, clears session “busy” status after interrupted turns, bounds telemetry flushing during shutdown, and allows fully analyzable read-only shell pipelines into execution-evidence review while requiring explicit approval for incomplete/unbound pipelines. The preceding **v1.0.90 (2026-09-30)** includes recovery of MCP tools after transient discovery failures without restarting, retaining unchanged catalogs during recovery. These are concrete resilience and operator-feedback changes; release notes provide no latency, throughput, or resource numbers. **Certainty:** high for listed release contents; no independent corroboration of the release claims. **IssueOps applicability:** useful comparison points for bounded shutdown/telemetry, interrupted-run visibility, and recovery semantics; not evidence that adopting them improves IssueOps performance. Sources: [v1.0.91 release](https://github.com/github/copilot-cli/releases/tag/v1.0.91), [official release index](https://github.com/github/copilot-cli/releases).

2. **Dynamic workflows add a code-defined orchestration surface in public preview.** Announced **2026-10-01**, dynamic workflows are programs inside CLI extensions that combine deterministic steps with one or more agents, sequence or parallelize tasks, pass structured results, pause for review, and preserve resumable run results. Docs also describe concurrency/total-agent, time, and approximate-credit limits, plus a `/workflows` view of phases, progress messages, subagents, and AI-credit usage. They require `--experimental` or `/experimental on` in CLI. The official changelog and official docs agree on the feature, but are same-publisher sources, not independent corroboration; both characterize it as preview/subject to change. **Certainty:** high for documented behavior and preview status. **Applicability:** a lead for studying explicit stage boundaries, structured evidence handoffs, and visible progress in IssueOps loops; it does not establish a faster execution path, and Copilot workflow state/permissions are not IssueOps contracts. Sources: [2026-10-01 announcement](https://github.blog/changelog/2026-10-01-dynamic-workflows-in-copilot-cli-and-the-copilot-app/), [dynamic workflow documentation](https://docs.github.com/en/copilot/concepts/agents/dynamic-workflows).

3. **Cross-client plugin packaging is GA, while Copilot-specific behavior remains namespaced.** GitHub’s **2026-08-12** announcement says Agent Plugins 1.0 was published on **2026-08-06** and is generally available in Copilot CLI and other compatible clients. The standard packages skills and MCP servers; Copilot-specific agents, commands, rules, and hooks go in `com.github.copilot/`. Existing Copilot plugins remain supported. **Certainty:** high as an official product announcement; independent implementation/interoperability confirmation was not found in this bounded search. **Applicability:** supports evaluating portable packaging for existing host-neutral IssueOps skills, while retaining thin host adapters. The announcement is not evidence that IssueOps should add a plugin or duplicate its current shared-skill source. Current local design already keeps `skills/` as the common source and host integrations thin (`.issueops/architecture/host-integration.md:1,39,81-85`). Source: [Agent Plugins 1.0 announcement](https://github.blog/changelog/2026-08-12-agent-plugins-1-0-in-vs-code-copilot-cli-and-the-copilot-app/).

4. **Extensions expose tools and slash commands, but execute locally with user privileges.** The official CLI documentation describes extensions as separate Node.js processes that can add callable tools and user-invoked commands; lifecycle-aware extensions can observe sessions and maintain state across tool calls. They are experimental, require the experimental switch, and can be disabled or restricted to “Load Only” so the agent cannot manage extension code. The docs explicitly warn that extension code runs with the user’s privileges. A configuration reference separately documents `~/.copilot/logs/`, extension logs, session event logs, and session-history artifacts. **Certainty:** high for documented interfaces and trust boundary; no independent validation or reliability/performance comparison. **Applicability:** possible visibility instrumentation lead, but local extensions are not a reason to move IssueOps authority out of its CLI/MCP core. IssueOps already records checkpoints and exposes self-verify history/compare/promote (`.issueops/architecture/runtime.md:44,58`). Sources: [CLI extensions](https://docs.github.com/en/enterprise-cloud%40latest/copilot/concepts/agents/copilot-cli/about-cli-extensions), [configuration directory reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference).

## Evidence classification and local fit

All product and capability claims above are official GitHub/GitHub Docs claims. Cross-page matches (for example, changelog plus docs for dynamic workflows) are **same-publisher corroboration**, not independent corroboration. No independent source was used to validate implementation or outcomes. Local anchors show IssueOps already favors shared host-neutral skills, CLI/MCP consistency, state checkpoints, and explicit architecture boundaries (`.issueops/architecture/host-integration.md:39,81-85`; `.issueops/architecture/runtime.md:44,58`). The evidence therefore suggests investigation targets, not a change request. `.issueops/CONSTITUTION.md:44-55` prioritizes correctness and measured bottlenecks over speculative optimization.
