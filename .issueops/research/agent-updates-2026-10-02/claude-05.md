# Claude subagents and task concurrency

Retrieved: 2026-10-02. This is one bounded evidence lane for IssueOps performance, optimization, and visibility. Official-source claims below are not independently corroborated by a second publisher; repository anchors establish local applicability, not independent validation of Anthropic’s product claims.

## Findings

1. **Ordinary subagents trade context isolation for separate work and usage.** Claude Code documents that each subagent has its own context window, prompt, tools, and permissions; results return to the caller, while named subagents can also message each other. Their requests count against the same usage limits as the main conversation. Built-ins include read-only Explore and Plan agents, while general-purpose agents cover multi-step work. (Official, single source: [Create custom subagents](https://code.claude.com/docs/en/sub-agents), retrieved 2026-10-02; page describes Claude Code v2.1.198 behavior for Explore, but gives no publication date.) **Certainty: high** for documented behavior. **Applicability:** IssueOps can use narrow, read-only exploration to keep bulk search output out of the main context, but should compare saved context against added model usage and spawn overhead. **Counterevidence:** documentation does not quantify latency, token savings, or a universal performance win; Claude’s main conversation can itself perform small, tightly scoped work.

2. **Agent teams are a distinct, coordination-heavy mode, not a free increase in subagent concurrency.** The official guide says teams are experimental, disabled by default, require an interactive session, and have no hard teammate-count limit; token usage scales linearly, coordination overhead rises, and returns diminish. Teammates use a shared task list with dependencies and file locking for concurrent claims. The guide recommends starting with 3–5 teammates, and warns of resume, task-status, shutdown, and nesting limitations. (Official, single source: [Orchestrate teams of Claude Code sessions](https://code.claude.com/docs/en/agent-teams), retrieved 2026-10-02; no guide release version/date stated.) **Certainty: high** for documented constraints and recommendation; the sizing guidance is Anthropic’s heuristic, not an independent benchmark. **Applicability:** parallelize independent research/review slices with explicit ownership and monitor/steer; do not infer speedup from agent count. Keep durable IssueOps work in child cycles rather than treating an ephemeral team task list as lifecycle authority. **Counterevidence:** teams allow direct peer messaging and shared task coordination when work genuinely needs discussion, which ordinary subagents do not provide to the same degree.

3. **Dynamic workflows expand the scale, with material usage and verification tradeoffs.** Anthropic’s May 28, 2026 announcement says workflows dynamically plan and run tens to hundreds of parallel subagents, check results, and save progress so interrupted runs can resume. The post says they are generally available across Claude Code CLI, Desktop, VS Code, and API, while warning of substantially higher token consumption. It does not state a Claude Code version number or publish a controlled performance comparison. (Official, single source: [Introducing dynamic workflows in Claude Code](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code), dated 2026-05-28; retrieved 2026-10-02.) **Certainty: high** that the announcement makes these availability/capability claims; **low** for general speedup because no comparable measurements are supplied. **Applicability:** a candidate for large, partitionable audits or migrations, not routine IssueOps tasks. Preserve IssueOps’ separate acceptance and ownership gates; workflow result verification is not equivalent to parent accept/reject. **Counterevidence:** the same announcement stresses substantially higher usage; the showcased Bun port is an Anthropic-reported case, not independent or general evidence.

4. **Task visibility has concrete native surfaces, while no ordinary-agent concurrency cap is established here.** Claude Code’s changelog labels v2.1.287 as October 1, 2026 and adds an `n:<text>` filter to the agents view; v2.1.286 (September 30) fixes several subagent/task visibility and completion issues, including foreground subagents missing task tools and background jobs appearing done while awaiting approval. (Official, single source: [Claude Code changelog](https://code.claude.com/docs/en/changelog), retrieved 2026-10-02.) **Certainty: high** for these release-note entries and dates. **Applicability:** use `/tasks` or the agents view as native, transient visibility, and capture measurable local signals (active/blocked/completed counts, wait duration, retries, model) before proposing IssueOps changes. The current IssueOps contract already separates transient native fan-out from durable child-cycle ownership (`.issueops/AGENT_WORKFLOW.md:81-83`); subagent use is exceptional and pattern-bound (`.issueops/SUB_AGENT_PATTERNS.md:7,35,84-100`), while optimization must target measured bottlenecks (`.issueops/CONSTITUTION.md:48,54-55`). **Counterevidence:** release-note fixes show these visibility surfaces have had defects; they do not expose durable, cross-host IssueOps state. The official pages fetched here do not establish a numeric concurrency limit for ordinary subagents.

## EXPAND

- Check the current official sub-agent/workflow docs for a documented ordinary-subagent concurrency cap and any release-version mapping for dynamic workflows; the fetched changelog and guides did not settle either.
- If IssueOps later considers performance changes, benchmark a fixed, independent read-only workload in Claude with and without delegation, recording elapsed time, token usage, and result quality. No performance percentages are supported by this evidence lane.
