# OpenAI prompt caching: latency and usage accounting

**Retrieved:** 2026-10-02
**Scope:** One bounded evidence lane for IssueOps performance, optimization, and visibility. No runtime behavior or configuration was changed.

## Findings

1. **Caching is prefix reuse, not a general request-speed switch.** OpenAI says it can skip recomputing an eligible, exact matching prompt prefix and reduce input processing before response generation. New suffix tokens still need processing; the feature does not change output generation, and the cache hit is not guaranteed. The current guide distinguishes earlier models from GPT-5.6 and later: GPT-5.6 (released 2026-07-09) adds explicit breakpoint controls, while eligible prefixes need at least 1,024 visible tokens. Model, tools/order, selected settings, prefix contents, cache lifetime, machine routing, and request rate all affect reuse. **Certainty: high for documented API behavior; efficacy in a given workload is unmeasured. Applicability:** preserve stable prompt/tool prefixes and append changing context where the host or caller controls request assembly. **Counterevidence/limit:** stable conversation context alone is not a hit, and compaction or changed tools/settings can reduce reuse. These are OpenAI official, single-source behavior claims, not independently verified implementation facts. Sources: [Prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching#how-caching-works); [GPT-5.6 release, 2026-07-09](https://developers.openai.com/api/docs/changelog#jul-9).

2. **Latency benefit is specifically on prompt prefill / time to first token; OpenAI publishes no universal cache-hit speedup.** The official guide describes faster processing before the response starts but gives no caching latency percentage. A separate company, Tars, reports an observational production comparison for OpenAI requests with prompts of at least 4,000 tokens: median TTFT was 1,807 ms without a cache hit versus 838 ms when at least half the tokens were cached (data window 2026-08-23–09-21; release deployed 2026-09-08). Tars explicitly says the groups had different model and prompt-size mixes and this was not a controlled test. **Certainty: high that Tars published these observations; low that caching alone caused the difference. Applicability:** use as motivation to measure matched, same-model requests, not as an IssueOps forecast. **Counterevidence:** output generation and other latency components remain; neither source establishes a universal speedup. Classification: OpenAI statement is official single-source; Tars is independent, self-reported corroboration of a possible direction, not controlled causal evidence. Sources: [OpenAI guide](https://developers.openai.com/api/docs/guides/prompt-caching#why-prompt-caching-matters); [Tars case study, updated 2026-09-22](https://hellotars.com/blog/engineering/cutting-llm-costs-with-prompt-caching#latency).

3. **Usage visibility must distinguish reads, writes, and ordinary input, with model-specific rates.** For GPT-5.6 and later, Responses usage fields include `input_tokens`, `input_tokens_details.cached_tokens`, and `input_tokens_details.cache_write_tokens`; OpenAI’s guide shows ordinary input as total input minus cached and cache-write tokens, then applies model prices to each category. GPT-6.1 Sol (released 2026-09-29) lists $2/M ordinary input, $0.10/M cached input, and $2.50/M cache writes. On GPT-5.6 and later, writes cost 1.25× uncached input and reads are generally 0.1× (0.05× for GPT-6.1 Sol); earlier-model accounting differs. The Prompt Caching dashboard (released 2026-08-20) exposes hit rate, reads per write, and read/write/uncached breakdowns. **Certainty: high for published field meanings, release dates, and listed prices. Applicability:** any real OpenAI integration should retain per-response token categories and model identity rather than report only a hit ratio or estimated total. **Counterevidence:** a high cache-hit rate is not total-task savings; cached input remains billable. Agents API turn usage is best-effort and does not expose a separate cache-write count, so it cannot establish exact charges. Sources: [Usage and cost calculation](https://developers.openai.com/api/docs/guides/prompt-caching#monitor-cache-performance); [GPT-6.1 Sol model/pricing](https://developers.openai.com/api/docs/models/gpt-6.1-sol); [Dashboard release, 2026-08-20](https://developers.openai.com/api/docs/changelog#aug-20); [Agents usage limits](https://developers.openai.com/api/docs/guides/agents-api/observability#model-usage-and-cost).

4. **New diagnostics make cache misses observable, but have bounded scope.** Prompt Cache Diagnostics became generally available on 2026-09-08 for Responses API requests on GPT-5.6 and later supported models. With a prior response ID, a response can classify a comparison as hit, miss (with a reason), unavailable, or baseline-not-found. Its estimated comparison counts are not billing usage; use current response usage fields for actual reported reuse. The diagnostic request does not alter caching and records no raw prompt/output per the guide. **Certainty: high for documented scope and semantics. Applicability:** if IssueOps later calls this API, diagnostics plus token fields can classify cache-related latency/cost changes without logging prompt text. **Counterevidence:** records expire, results are best-effort and may identify only the first classified cause; this feature does not observe arbitrary Codex/Claude/Omo host calls. Source: [Diagnostics guide](https://developers.openai.com/api/docs/guides/prompt-caching/diagnostics); [GA release, 2026-09-08](https://developers.openai.com/api/docs/changelog#sep-8).

## IssueOps applicability

The repository’s performance guidance says to optimize only after a before/after duration identifies a concrete bottleneck, and records no measured daemon/MCP latency regression in the cited quality pass (`.issueops/issues/_unnumbered/issueops-performance-improvement.md:6`). Its provider decision is explicitly Z.AI-only until a second provider has a real caller (`.issueops/adr/decisions/2026-07-02-external-llm-zai-only.md:7-10`). Therefore OpenAI cache controls are not an immediate core optimization. The transferable lead is measurement discipline: where a host/provider exposes these fields, correlate per-model cache-read/write/input usage with request latency, without collecting prompt contents. Do not imply IssueOps currently receives OpenAI cache metrics.

## Source assessment

OpenAI’s guide, model page, changelog, and Agents API page are official primary sources from one provider; they are not independent corroboration. The Tars case study is independently published operational evidence, but self-reported and observational. No controlled independent latency benchmark was found in this bounded search.

## EXPAND

- Measure same-model, same-size request TTFT with and without cache reuse before assigning a latency effect; separate first-token from completion latency.
- Check whether each supported host exposes provider usage details at all, and whether reads/writes can be safely attributed by model or task without recording prompt text.
- Recheck provider-specific pricing and fields at implementation time: the verified GPT-6.1 Sol release is 2026-09-29 and the caching guide is model-dependent.
