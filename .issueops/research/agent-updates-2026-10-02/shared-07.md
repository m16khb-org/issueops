# Anthropic tool-result efficiency and context engineering

**Retrieved:** 2026-10-02
**Scope:** One bounded evidence lane for IssueOps performance, optimization, and visibility.
**Source independence:** The technical findings below come from Anthropic's own engineering posts, product announcements, and API documentation. These are official primary sources but all from one publisher; they are not independent corroboration. No independent benchmark was found or used. Percentages below are Anthropic-reported results, not IssueOps measurements.

## Findings

1. **Shape tool results before adding context, and measure the task rather than optimizing token count alone.** Anthropic recommends returning high-signal fields, semantic identifiers, pagination/range/filter/truncation for potentially large responses, and actionable errors; it also says response format and identifier style can change agent performance and should be evaluated. The [writing-tools guidance](https://www.anthropic.com/engineering/writing-tools-for-agents#optimizing-tool-responses-for-token-efficiency) specifically contrasts detailed and concise responses and recommends tracking accuracy, runtime, call count, token use, and errors. **Certainty: high** that this is Anthropic's published advice; efficacy depends on the tool and workload. **Applicability: high:** `.issueops/architecture/runtime.md#MCP-tool-design-guidance` already calls for bounded, task-specific tools and resources for reusable context; `.issueops/CONVENTIONS.md` further requires deterministic tool ordering. Candidate improvements should therefore be tested as response-shape or query-bound changes against representative tasks, with correctness and latency alongside output size. **Counterevidence:** Anthropic says there is no universally best response format, and its context-engineering post notes just-in-time exploration is slower than preloaded context. Do not truncate evidence needed for a decision simply to reduce tokens.

2. **Clearing stale tool results is a context-management feature, not a reason to discard the source of truth.** Anthropic's [context-editing announcement](https://www.anthropic.com/news/context-management) launched context editing and a memory tool with Sonnet 4.5 on **2025-09-29**. The current [context-editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing#tool-result-clearing) specify beta header `context-management-2025-06-27` and strategy `clear_tool_uses_20250919`: when a configured input-token threshold is exceeded, older tool results are replaced by placeholders while recent calls can be kept. The docs advise excluding tools where results remain relevant. **Certainty: high** for the documented API behavior and identifiers, but this is Anthropic-hosted behavior, not an IssueOps feature. **Applicability: medium:** it is useful precedent for long-running host sessions and for separating durable notes from replayed raw output; IssueOps' own `issueops mcp` is a local stdio server, not Anthropic's Messages API, so this feature cannot be assumed to manage its client transcript. **Counterevidence:** clearing can remove facts needed later, and the docs warn tool-result clearing invalidates cached prompt prefixes and incurs cache-write costs. Retain record/files as authoritative; treat transcript pruning as an independent host concern.

3. **For large multi-call workflows, transform results outside model context and return only the aggregate; do not add orchestration overhead to small calls.** Anthropic's [advanced-tool-use beta](https://www.anthropic.com/engineering/advanced-tool-use) (`advanced-tool-use-2025-11-20`) identifies Tool Search Tool (`tool_search_tool_*_20251119`), Programmatic Tool Calling (PTC), and tool-use examples. PTC uses `code_execution_20250825` to orchestrate tools and keep intermediate results out of model context; [API release notes](https://platform.claude.com/docs/en/release-notes/overview#june-18-2026) say SDK support for `code_execution_20260120`, the minimum PTC version, shipped **2026-06-18**. Anthropic reports an internal complex-research-task average decline from 43,588 to 27,297 tokens (37%), with accuracy changes on named internal benchmarks. **Certainty: high** that Anthropic published these figures and mechanisms; **low-to-medium** for transfer to IssueOps because evaluation design and workload equivalence are not independently established. **Applicability: low-to-medium:** consider only deterministic aggregation or filtering for large query results behind existing read-only boundaries. **Counterevidence:** PTC adds a code-execution step; Anthropic recommends it mainly for large datasets, multi-step workflows, filtering, or parallel operations, and says it is less useful for simple single-tool lookups or when the model must inspect intermediate evidence. Do not infer IssueOps savings from Anthropic's percentages.

4. **Tool discovery reduces definition context only when the catalog is large, and introduces a lookup step.** Anthropic's [advanced-tool-use post](https://www.anthropic.com/engineering/advanced-tool-use) and [tool-search docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool#when-to-use-tool-search) describe deferred loading and on-demand expansion, recommending it at 10+ tools or over 10K definition tokens; they call it less beneficial for fewer than 10 tools or compact definitions. Anthropic reports 85% lower definition-token use and higher tool-selection accuracy in its own examples. **Certainty: high** as an official single-source claim, not independently corroborated. **Applicability: medium:** compare against the actual host-advertised catalog and the relevant client; IssueOps already favors bounded tools, deterministic ordering, and external host adapters. **Counterevidence:** search adds latency, while local stdio clients may not implement Anthropic's `defer_loading`/`tool_reference` API semantics. Catalog size alone is not evidence that IssueOps should build a proprietary discovery layer.

## EXPAND

- **Actionable:** measure representative IssueOps MCP workflows for response bytes/tokens (where available), elapsed time, tool-call count, and task correctness; compare concise/filterable output with current output before proposing a change.
- **Actionable:** inspect the advertised tool count and descriptor size for each target host, then test whether native deferred loading exists before considering catalog-search work.
- **Not pursued:** an independent reproduction of Anthropic's reported percentages. No independent evaluation was identified in this bounded source set, and no IssueOps benchmark was run.
