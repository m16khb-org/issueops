# Agent Skills: progressive disclosure and portability

**Retrieved:** 2026-10-02
**Scope:** Public official documentation and repository guidance, as one bounded evidence lane for IssueOps performance, optimization, and visibility. This is a specification/documentation review, not a benchmark of host runtime behavior.

## Findings

1. **Progressive disclosure is the format’s central context-management mechanism, not a measured speed guarantee.** The current Agent Skills specification describes three levels: advertise each skill’s `name` and `description` at startup (~100 tokens), load full `SKILL.md` when activated (<5,000 tokens recommended), then read linked resources when needed. It recommends keeping the main file under 500 lines and references one level deep. Anthropic’s engineering explanation describes the same staged loading and says unused resources do not enter context; its page does not state a publication date. Anthropic’s official [skills launch post](https://claude.com/blog/skills) is dated 2025-10-16 and notes the open-standard publication update on 2025-12-18. Microsoft Learn, updated 2026-10-01, independently documents a four-stage variant adding on-demand script execution. **Certainty: high** for these documented design contracts; efficiency benefits are design rationale, not quantified outcome. **Applicability:** keep discovery descriptions compact, make the activated instructions concise, and split rarely needed details into focused references. **Counterevidence:** every skill description is still advertised; activation loads the whole main file, so oversized instructions and weak trigger descriptions can still consume context or select the wrong skill. Sources: [specification](https://agentskills.io/specification#progressive-disclosure) (undated/current page; retrieved 2026-10-02); [Anthropic engineering article](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) (publication date not stated); [Microsoft Learn](https://learn.microsoft.com/en-us/agent-framework/agents/skills) (updated 2026-10-01).

2. **Portability is strongest at the file-format boundary; execution and activation are not uniform.** The spec requires a skill directory and `SKILL.md`, with required `name` and `description`; resources and scripts are optional. `allowed-tools` is explicitly experimental, with implementation support varying. Anthropic’s current Claude Code docs say it follows the open standard but adds non-standard frontmatter and body features; only the standard fields are valid on Claude.ai/API upload paths. OpenAI’s official Skills guide says the format is compatible with the standard, while distinguishing hosted `skill_reference` attachments from local-shell path configuration and Agents API capability directories. This is **independent official corroboration by adopter documentation**, not proof every adopter implements every feature. **Certainty: high** for documented field and setup differences. **Applicability:** make shared IssueOps skills standard-first; isolate host-specific metadata or invocation assumptions in adapters, and test the same skill in each supported host. **Counterevidence:** Claude Code states standard frontmatter works there unchanged, and OpenAI states skills are compatible with the standard; file portability is real even when deployment differs. Sources: [spec](https://agentskills.io/specification#frontmatter); [Claude Code skills docs](https://code.claude.com/docs/en/skills#using-skill-frontmatter-outside-claude-code) (live documentation cites Claude Code versions including v2.1.286; page publication date not stated); [OpenAI Skills guide](https://developers.openai.com/api/docs/guides/tools-skills) (page publication date/version not stated).

3. **Bundled scripts and references extend the format, but portability does not imply common execution semantics or trust.** The spec says agents may load resources on demand and that supported script languages depend on each implementation. Anthropic’s engineering article argues deterministic code can be more efficient/reliable than token-generated operations, but provides no general measured performance delta. OpenAI’s guide classifies skill instructions as privileged input that can influence tool use and warns about prompt injection/data exfiltration; Microsoft’s 2026-10-01 docs require approval for skill tools by default and distinguish read-only resource tools from script execution. **Certainty: high** for the distinct documented controls; **single-source** for Anthropic’s comparative efficiency rationale. **Applicability:** use references for conditional detail; keep scripts narrow, reviewable, and covered by IssueOps’s existing validation and host behavior checks. Do not claim token or latency savings without cross-host runs. **Counterevidence:** some consumers can load resources without reading them into context, but others may not expose the same resource/script tools.

4. **The project’s one-source strategy matches the portable-format model, but its own skill inventory documentation currently conflicts.** `.issueops/conventions/go-and-packages.md:141-147` says `skills/<name>/` is canonical and requires `SKILL.md`, while `.issueops/architecture/host-integration.md:39` claims 52 shared skills and `.issueops/TECH_STACK.md:55` claims 34. `.issueops/architecture/host-integration.md:64` says per-skill contracts are authoritative; `.issueops/TECH_STACK.md:86` documents user-scope links for Codex, Claude, and Omo. **Certainty: high** that the cited documents disagree; the actual inventory was not established in this bounded evidence pass. **Applicability:** treat the source directory and live inventory command as the authority before using counts in visibility dashboards; reconcile the documentation separately. **Counterevidence:** both inventory statements direct readers to live inspection, so the inconsistency does not establish the current count.

5. **Performance and visibility should be evaluated from traces, not inferred from file size or vendor claims.** OpenAI’s official skill-evaluation article recommends testing expected and unexpected activation, recording agent traces and artifacts, checking skill invocation and expected commands, and tracking command count and token usage for thrashing/context bloat. It suggests a small targeted prompt set and deterministic graders before qualitative grading. This is **single-source product guidance**, not a published comparative result; the page does not state a publication date or product version. **Certainty: high** that the guidance is published; no empirical reduction is established. **Applicability:** use activation precision, resource reads, input tokens, command count, and task success as shared-skill visibility measures across hosts. **Counterevidence:** token/trace availability and event schemas are host-specific, so numbers need not be directly comparable without normalization. Source: [Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills) (retrieved 2026-10-02; publication date/version not stated).

## Source classification

The Agent Skills specification and Anthropic are authoritative for the original format and Anthropic behavior, but are not independent corroborators of each other’s product claims. OpenAI and Microsoft are separate official adopter documentation and corroborate standard-format adoption while documenting their own execution surfaces. OpenAI’s evaluation article is product guidance only. None of these sources is an independent performance study.
