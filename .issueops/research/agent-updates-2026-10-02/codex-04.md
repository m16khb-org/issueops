# Codex context compaction and prompt caching

Retrieved: 2026-10-02
Scope: one evidence lane for IssueOps performance, optimization, and visibility. This report separates the Codex client from OpenAI's Responses API; API controls must not be assumed to exist in Codex CLI.

## Findings

1. **Codex documents automatic history compaction as a configurable client behavior, but a newer context-management mode is not presently available.** The live official Codex configuration reference describes `model_auto_compact_token_limit` (unset means model defaults), `model_auto_compact_token_limit_scope` (`total` or `body_after_prefix`), and `model_context_window`. It separately labels `features.context_management.experimental_mode` “not currently available.” This is evidence for the ordinary auto-compaction controls, not proof that the experimental mode ships or can be enabled. Source: [Codex Configuration Reference](https://learn.chatgpt.com/codex/config-file/config-reference), retrieved 2026-10-02; no release version/date is attached to this live reference. **Certainty: high** for documented configuration; **medium** for current availability because the page is live documentation, not a version-pinned binary check. **Applicability:** measure and tune the existing auto-compact threshold only against the installed Codex version; do not recommend enabling the experimental flag from this page.

2. **OpenAI API prompt caching is prefix reuse, not a session-level guarantee.** Official docs say the rendered prefix—including instructions and tool definitions—must match; dynamic edits before a cache boundary, tool/schema changes, and compaction can reduce reuse. For GPT-5.6 and later, the documented minimum cacheable visible prefix is 1,024 tokens; caching controls and the GPT-5.6 family were announced 2026-07-09. The docs recommend measuring `cached_tokens`, `cache_write_tokens`, latency, and total input cost rather than inferring savings from cache-hit percentage. Sources: [Prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching) and [API changelog, 2026-07-09](https://developers.openai.com/api/docs/changelog#july-2026). **Certainty: high** as official API documentation. **Applicability:** useful design evidence for stable shared instructions/tool catalogs, but these Responses API controls and thresholds are not evidence of Codex CLI’s internal cache implementation.

3. **Compaction trades a smaller next context against possible cache reuse loss; visibility tools can classify this explicitly in the API.** The Responses compaction guide describes server-side compaction launched 2026-02-10 and context reduction for long interactions; the cache guide says changed compacted prefixes may reduce reuse even if fewer input tokens can lower total cost. Prompt Cache Diagnostics became generally available for GPT-5.6+ Responses API models on 2026-09-08; it can report `context_compacted` and recommends comparing token usage and total cost. Sources: [Compaction guide](https://developers.openai.com/api/docs/guides/compaction), [API changelog, 2026-02-10](https://developers.openai.com/api/docs/changelog#february-2026), [Prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching#compaction-can-reduce-cache-reuse), [Diagnostics guide](https://developers.openai.com/api/docs/guides/prompt-caching/diagnostics), and [API changelog, 2026-09-08](https://developers.openai.com/api/docs/changelog#september-2026). **Certainty: high** for API behavior; **not established** for equivalent Codex CLI diagnostics. These sources are all first-party OpenAI publications, so they are not independent corroboration.

4. **IssueOps already handles compact lifecycle context, while its documented token-usage visibility is scoped to separate external LLM calls.** The 2026-08-27 ADR says Codex `SessionStart` receives `source: compact` and re-injects the project-doc catalog; its evidence records Codex 0.150.1 behavior and cites the official hook contract (`.issueops/adr/decisions/2026-08-27-session-start-owns-compaction-context.md:9-19`). The host integration map places that hook in the recommended Codex setup (`.issueops/architecture/host-integration.md:9-17`). A separate 2026-07-02 ADR records provider/model/token/duration for IssueOps external LLM calls (`.issueops/adr/decisions/2026-07-02-external-llm-usage-observation.md:5-14`); it does not establish Codex-host turn usage. **Certainty: high** for what these project records document. **Applicability:** preserve the existing compact re-injection contract; treat Codex context/cache metrics as a distinct visibility gap unless the host exposes them in a supported surface.

## Counterevidence and source quality

A 2026-09-07 OpenAI Community post attributes a three-part experimental context manager to Codex 0.153.4 and gives a config flag: [community post](https://community.openai.com/t/experimental-context-management-compaction-in-codex/1395578). This is a forum report, not an official release note or independent implementation verification. The fetched official [0.153.4 release page](https://github.com/openai/codex/releases/tag/rust-v0.153.4) lists two model-picker/guidance fixes and does not corroborate that feature. The official current config reference’s “not currently available” wording is contrary evidence to treating the forum instructions as currently usable. No independent source corroborating the experimental-mode claim was found.

No cited source was inaccessible. The repository CodeGraph lookup (`codegraph explore "issueops context compaction prompt caching token visibility performance optimization"`) exited 1, so repository applicability was checked against the cited ADR and architecture files directly.

## EXPAND

- **Codex CLI version-pinned behavior:** inspect official Codex source/release notes for the actual `model_auto_compact_token_limit_scope` semantics and whether the reported experimental mode ever shipped; the versioned source is actionable because current docs and the 0.153.4 forum report conflict.
- **Host-level observability:** verify supported Codex status/events for context-window pressure, compaction counts, cached input, and per-turn usage. This determines whether IssueOps can surface metrics without relying on undocumented internals.
- **IssueOps baseline:** if the host provides supported measurements, compare representative repeated tasks before/after compact events using input tokens, cache reads/writes, latency, and total cost. Do not infer improvement from cache-hit rate alone.
