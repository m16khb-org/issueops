# Claude evidence lane: releases, breaking changes, and IssueOps relevance

**Retrieved:** 2026-10-02
**Scope:** Claude Code CLI and Anthropic-operated Claude API. Release dates are from the official GitHub Releases API; release behavior is from Anthropic's release notes. “Breaking” below means a dated behavior or compatibility change that can disrupt an existing caller/configuration, not that Anthropic labels the release a major version. Official-source claims are not independently corroborated unless explicitly stated.

## Findings

1. **Latest stable Claude Code release is v2.1.287 (2026-10-01).** The official releases endpoint lists it first; its metadata says `prerelease: false`, `immutable: true`, and `published_at: 2026-10-01T18:00:22Z`. The notes add a searchable `n:<text>` filter to the agents view and add `prompt_text` to the OpenTelemetry `user_prompt` event, explicitly telling collectors to drop or mask it wherever they handle `prompt`. The same release corrects the transcript/debug summary so Claude Code's internal hook callbacks are not counted as configured hooks. **Certainty: high** for published metadata and listed behavior; single official source (release record), no independent corroboration. **Applicability: medium-high**: searchable background work and more accurate hook counts are useful visibility patterns for IssueOps; added prompt telemetry has privacy/redaction implications and is not a request to copy the field or host-specific behavior. Counterevidence: the release notes describe product behavior, not an IssueOps integration or measured operational gain. [Release record](https://github.com/anthropics/claude-code/releases/tag/v2.1.287); [official metadata](https://api.github.com/repos/anthropics/claude-code/releases/tags/v2.1.287).

2. **v2.1.286 (2026-09-30) reports performance changes without benchmarks or a performance percentage.** Its notes say per-turn performance improves when many permission-deny rules and MCP tools are configured, SDK/`-p` sessions respond better to repeated enables of an already connected MCP server, and a long-session transcript view responds faster. They also bound failed API retries to a single whole-model-call budget, “at most 14 requests” under default retry settings. This is a useful precedent for IssueOps performance work: state the workload and observable boundary, then benchmark locally instead of borrowing a vendor claim as a percentage. **Certainty: high** for what the release claims; performance impact for IssueOps remains unmeasured. **Applicability: medium**: MCP tool count and repeat initialization are potential analogue workloads, not proof the Go core has the same bottleneck. Counterevidence: no benchmark data or cross-version comparison is included. [Release record](https://github.com/anthropics/claude-code/releases/tag/v2.1.286); [official metadata](https://api.github.com/repos/anthropics/claude-code/releases/tags/v2.1.286).

3. **Dated Claude Code compatibility changes in v2.1.286 can alter existing automation.** `--bare` now connects only MCP servers named on the command line, omits model system reminders, starts no background tasks, and stops a timed-out shell instead of moving it to the background. Plugin installation also now refuses npm sources that are git repositories or folders and installs dependencies only from registry packages. These are concrete compatibility edges for scripts that relied on implicit MCP discovery, session reminders, background continuation, or non-registry plugin sources. **Certainty: high** that these are in the official notes; no separate migration notice or independent corroboration found. **Applicability: low-medium**: IssueOps should not adopt Claude-specific settings, but any Claude-backed integration or operator documentation that invokes these paths should test assumptions. Counterevidence: the project describes host integrations as thin adapters around a shared core, not as a Claude Code plugin installer. [Release record](https://github.com/anthropics/claude-code/releases/tag/v2.1.286); [official metadata](https://api.github.com/repos/anthropics/claude-code/releases/tags/v2.1.286); [IssueOps host boundary](../../architecture/host-integration.md) (lines 1-15).

4. **Anthropic dated a coming Claude API model retirement on 2026-09-30.** `claude-sonnet-4-5-20250929` became deprecated that day and has a tentative retirement date of 2026-11-30; the documented replacement is `claude-sonnet-5-5`. Anthropic says dates apply to its own API, Claude Platform on AWS, and Microsoft Foundry; Bedrock and Google Cloud maintain separate schedules. Retirement means requests to a retired model fail. **Certainty: high** for the documented API lifecycle and scope; one official Anthropic documentation source, without independent corroboration. **Applicability: low for current role defaults**: the IssueOps ADR index records Opus 5 for planning/review and Sonnet 5 for implementation (2026-09-24), not Sonnet 4.5. Still actionable for any pinned legacy model IDs in code, scripts, or external providers. Counterevidence: this lane did not inspect production configuration or user state, so it establishes no such pin exists. [Deprecations](https://platform.claude.com/docs/en/about-claude/model-deprecations); [IssueOps ADR index](../../ADR.md).

## Source independence and EXPAND

GitHub release pages, their API metadata, and the changelog are one publisher's release record, not independent corroboration. Anthropic's model-lifecycle documentation is a separate official document but not an independent organization/source. No third-party source was used to upgrade certainty.

**EXPAND:** Check the next Anthropic release and verify whether any deployed Claude-backed integration pins Sonnet 4.5 or depends on the changed `--bare`/plugin-install behavior. Reason: this bounded lane did not inspect production code, configuration, installation, or user state; both checks are actionable and require a separate scope. No performance percentage is supportable from these release notes.
