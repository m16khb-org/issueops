# Codex Skills, AGENTS.md, and Plugin Distribution

Retrieved: 2026-10-02. Scope: public OpenAI/Codex sources and this repository. Five findings below are evidence for future issueops performance, optimization, and visibility work, not claims that the repository currently has a measured bottleneck.

## Findings

### 1. Skill metadata and instruction bodies are separate context costs

OpenAI's GPT-6 Astra skills/prompt guidance says Codex first sees skill names and descriptions, then loads full instructions when a request matches. It warns that long descriptions and a large skill set can cause descriptions to be shortened, reducing selection clarity; it recommends concise trigger descriptions and progressive disclosure (small router `SKILL.md`, supporting references loaded when needed). It also cautions that elaborate recipes can overconstrain stronger models. Source: [OpenAI Developers, “Rethinking skills and prompts for GPT-6 Astra”](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra), fetched 2026-10-02; the fetched body does not show a publication date or article version. **Certainty:** high that this is OpenAI's stated guidance; no independent corroboration found. **Applicability:** directly supports measuring frontmatter-description budget and full skill reads separately before trimming or splitting issueops skills. **Counterevidence:** the article gives no issueops-specific measurements or performance percentages, and detailed procedures remain useful when their workflow is actually invoked.

### 2. AGENTS.md has deterministic layering and an observable size ceiling

The official Codex instructions guide says the instruction chain is built at run/session start from global Codex-home instructions and project path instructions, with nearer files later in the merged prompt; `AGENTS.override.md` takes precedence per directory. It documents a default combined project-instruction cap of 32 KiB, `project_doc_max_bytes` to change it, and TUI/session logs to inspect loaded sources. Source: [ChatGPT Learn, “Custom instructions with AGENTS.md”](https://learn.chatgpt.com/codex/guides/agents-md), fetched 2026-10-02; the page did not expose a publication date or product version. **Certainty:** high as official Codex documentation; it is a single-source claim, not independently corroborated here. **Applicability:** add an evidence-based inventory of loaded instruction files, aggregate bytes, and truncation in clean-session tests to improve visibility and find oversized always-read guidance. **Counterevidence:** a size cap is not proof the current issueops instructions exceed it; this session did not inspect the user's Codex home or capture a Codex session log.

### 3. Codex plugin distribution now has distinct public and private paths

OpenAI's current package guide defines a portable root `plugin.json` with optional `skills/`, `mcp.json`, assets, and hooks; a Codex compatibility manifest remains supported. It distinguishes the public Plugins Directory shared by ChatGPT and Codex from local/repo/personal marketplaces used for testing and team distribution, and documents Git and npm marketplace sources. Source: [OpenAI Developers, “Package your plugin”](https://developers.openai.com/plugins/build/plugins), fetched 2026-10-02; no page date/version is stated. OpenAI's announcement reports six role plugins bundling apps, skills, instructions, and workflows, with 62 apps and 110 skills: [“Codex for every role, tool, and workflow”](https://openai.com/index/codex-for-every-role-tool-workflow/), fetched 2026-10-02. Both are first-party OpenAI sources, not independent corroboration. **Certainty:** high for the documented packaging/distribution capabilities; announcement counts are OpenAI's claims. **Applicability:** assess an optional Codex plugin package/marketplace as a discovery and selective-distribution layer, while preserving the existing CLI/MCP core. **Counterevidence:** public submission has review and package requirements; plugin installation is not equivalent to issueops native install, and repo marketplace files introduce a separate surface to test.

### 4. A concrete plugin-loading optimization shipped in Codex CLI 0.160.0

The official [OpenAI Codex v0.160.0 release](https://github.com/openai/codex/releases/tag/rust-v0.160.0) was published 2026-10-01 (release API: [`published_at`](https://api.github.com/repos/openai/codex/releases/tags/rust-v0.160.0), 2026-10-01T20:19:13Z; `prerelease: false`). Its notes say plugin workflows cache parsed manifests and reuse an HTTP connection pool for remote plugin requests, “reducing repeated plugin-loading work” ([PR #49099](https://github.com/openai/codex/pull/49099), [PR #49100](https://github.com/openai/codex/pull/49100)). **Certainty:** high that these changes are included in the published release notes; source is OpenAI's own repository, not independent performance evidence. **Applicability:** relevant to Codex plugin metadata/discovery overhead, and a useful signal to instrument repeated parsing and remote fetches in issueops if it adds comparable distribution behavior. **Counterevidence:** no latency or resource percentage is published; the change does not measure skill selection quality, AGENTS.md loading, or issueops performance.

### 5. issueops currently integrates Codex as native links plus MCP/hook, not a plugin

The repository's host map specifies `AGENTS.md`/shell as minimum Codex integration and user-scope `~/.codex/skills`, MCP config, and SessionStart context hook as recommended; it says plugin core logic is excluded and repo files are not created by default (`.issueops/architecture/host-integration.md:9-17`). The installer plans user skill links and Codex MCP/hooks (`internal/adapter/codex/install.go:18-36`); the hook implementation defines only SessionStart (`internal/adapter/codex/install_hooks.go:75-89`). This is corroborated by the implementation within the repository, not independent evidence about Codex. **Certainty:** high for this checkout's documented and coded install path. **Applicability:** current approach fits the thin-adapter architecture; plugin work should be evaluated as optional discovery/distribution, not a core rewrite. **Counterevidence:** native links may remain simpler and lower-friction for first-party developer workflows than a marketplace package.
