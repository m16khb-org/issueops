# Durable execution: idempotency, checkpoints, replay

**Retrieved:** 2026-10-02
**Scope:** One bounded evidence lane for shared IssueOps performance, optimization, and visibility work. External evidence below is from product owners' public documentation or release metadata. Vendor docs are independent primary sources from separate organizations, not independent empirical evaluations; no third-party corroboration or benchmark was found in this lane.

## Findings

1. **Replay preserves decisions, but its input grows with history.** Temporal says a Workflow Task replays the complete Event History from the beginning; completed Activity and Timer results are read from history rather than re-running those operations. The task doc calls typical Workflow Task execution milliseconds and excludes Activity/Timer duration. That supports a distinction between repeated workflow-decision CPU and external-work latency, not a performance percentage. A growing history is a plausible replay-cost lead, but the cited page does not quantify growth or recommend a threshold. **Certainty:** high for the mechanism, medium for the cost implication. **Applicability:** measure IssueOps repeated orchestration and receipt reconstruction separately from external calls. **Counterevidence:** Temporal describes replay as typically fast; avoid assuming it is the current bottleneck. Sources: [Tasks](https://docs.temporal.io/tasks); server release metadata for `v1.31.0`, published 2026-04-29 ([official release](https://github.com/temporalio/temporal/releases/tag/v1.31.0), [API metadata](https://api.github.com/repos/temporalio/temporal/releases/tags/v1.31.0)). The docs are living, not pinned to that release; the release date is outside the preferred 90-day window and is context, not proof this behavior shipped in v1.31.0.

2. **Checkpoint granularity trades repeated work and visibility against persistence activity.** LangGraph describes checkpointing at node boundaries: on resume, work restarts at the beginning of the interrupted node. Smaller nodes reduce the amount of work that can be repeated and expose intermediate decisions, while producing checkpoints more often. The same page says async durability avoids waiting for writes by default, whereas `sync` waits and `exit` checkpoints only on completion. These are explicit product-doc tradeoffs, not independently measured latency results. **Certainty:** high for documented behavior; low for any quantitative performance prediction. **Applicability:** if IssueOps needs finer progress visibility, first measure checkpoint/write frequency and repeated node work. **Counterevidence:** the docs state async checkpoints have minimal performance impact; verify under this repository’s SQLite and workload before adopting more boundaries. Source: [Thinking in LangGraph, “Node granularity trade-offs”](https://docs.langchain.com/oss/javascript/langgraph/thinking-in-langgraph). Related release context: `langgraph==1.2.12`, published 2026-09-21 according to official [PyPI release metadata](https://pypi.org/pypi/langgraph/1.2.12/json); that release does not establish when the documented behavior was introduced.

3. **A durable step receipt is not exactly-once side-effect protection.** Inngest saves completed step results and reuses them on retry, but code outside steps runs again. Its docs explicitly warn that a provider can accept a write before the step result is recorded, so retry may repeat the external call. Event/function idempotency is separately scoped and documented as a 24-hour deduplication window; paused-function behavior can ignore it. **Certainty:** high for the stated product contract. **Applicability:** preserve distinct stable operation identity, durable intent/receipt, and reconciliation for IssueOps external mutations; test the “provider succeeded, local receipt missing” window. **Counterevidence:** step results prevent repeating already-recorded successful steps, but do not close the unrecorded-response gap. Source: [Inngest Idempotency](https://www.inngest.com/docs/durable-execution/guides-and-advanced/idempotency) and [Primitives and steps](https://www.inngest.com/docs/durable-execution/primitives). These living docs expose no release version/date; retrieval date is given above, and no relevant dated release was verified.

4. **IssueOps already applies request identity and fencing at its Orca boundary.** `internal/adapter/orca/client_orchestration.go:552-583` validates the retry request ID, sends it as `--retry-request`, then rejects a returned durable request ID that differs. `internal/adapter/orca/execution_test.go:176-211` covers empty, mismatched, and exact retry IDs. The architecture records one execution per row with a generation-fenced lease and says reconcile handles one current durable stage using bounded retry/CAS (`.issueops/architecture/issueops.md:11,30`). **Certainty:** high for this code and documented contract. **Applicability:** future optimization should preserve identity/fencing and compare stage-level latency/retry/ambiguity counts before changing checkpoint cadence. **Counterevidence:** these safeguards prove identity validation, not a measured replay bottleneck or comprehensive visibility of replay cost.

## Synthesis

Across the three vendor sources, durable recovery relies on saved results plus stable operation identity, but checkpoint placement and replay granularity determine how much decision work repeats. None establishes that IssueOps should add checkpoints or that replay currently dominates runtime. Treat event/history size, step replay count, external retry/ambiguous outcomes, checkpoint bytes/write latency, and visible stage age as measurement candidates—not claimed performance gains. External findings are separate vendor statements, not independent corroboration; repository evidence confirms related local safeguards but is not evidence for vendor performance claims.
