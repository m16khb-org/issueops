# Codex session recovery, background tasks, and worktrees

Retrieved 2026-10-02. Scope: official public Codex sources and this repository. External claims below are attributed to OpenAI's official product documentation or OpenAI's Codex CLI release notes; these are primary, single-publisher sources, not independent corroboration. No independent corroboration was established. Documentation pages are undated and unversioned where noted; the dated CLI release is 0.160.0 (2026-10-01).

Access note: the legacy `https://developers.openai.com/codex/release-notes/` URL returned “Page not found”; the current official changelog at `https://learn.chatgpt.com/docs/changelog` was fetched and used instead.

## Findings

1. **Recent CLI work targets recovery visibility and safer continuation.** Codex CLI 0.160.0 (2026-10-01) adds pagination to older tasks in the agent command center, restores saved permissions when resuming, and fixes queued-message recovery so unsent input resumes after reconnect only after uncertain submissions are resolved, avoiding duplicate sends. It also fixes incorrect resume/fork history selection and settings preservation in the terminal UI. These are concrete recovery and visibility changes, not evidence of a measured throughput gain. **Certainty: high** for the shipped release-note claims. **Applicability:** IssueOps can prioritize visible lifecycle/history and idempotent reconnect behavior when improving its own session handoff and status surfaces. **Counterevidence/limit:** this documents Codex CLI behavior, not a guarantee that IssueOps can inspect or control Codex's internal session state. Source: [Codex CLI changelog, 0.160.0, dated 2026-10-01](https://learn.chatgpt.com/docs/changelog).

2. **Scheduled work can either continue a chat or create fresh run contexts, and the local execution boundary matters.** Current official scheduled-task docs (unversioned; retrieved 2026-10-02) distinguish tasks scheduled inside an existing chat, which reuse its context, from standalone scheduled tasks, which start a new chat for each run. Local project tasks require the computer on, the desktop app running, and the project still on disk. In Git repositories, a task may run in the local checkout or a dedicated background worktree; local mode can change files still being edited, while a worktree isolates task changes. Findings appear in the Scheduled view. **Certainty: high** for documented product behavior. **Applicability:** choose persistent context for continued work; use isolated worktrees for independent scheduled work, and expose task/run status separately from execution authority. **Counterevidence/limit:** these are desktop-product behaviors and depend on machine/app availability; the docs make no latency or completion-time claim. Source: [Scheduled tasks](https://learn.chatgpt.com/docs/automations).

3. **Managed worktrees provide a recovery path, but snapshots are not equivalent to a durable execution record.** Current official worktree docs (unversioned; retrieved 2026-10-02) say a chat returns to its associated worktree after handoff; managed worktrees default to the latest 15, protect pinned, in-progress, and permanent worktrees from automatic deletion, and snapshot a managed worktree before deletion so a reopened chat can offer restoration. Archiving a chat can trigger deletion. Worktrees are Git-backed, usually detached HEAD, and `.worktreeinclude` controls copying ignored setup files. **Certainty: high** for the documented behavior. **Applicability:** recovery visibility should distinguish chat history, live workspace, and restorable snapshot; retention and disk-pressure cleanup need explicit status. **Counterevidence/limit:** ignored files not included by `.worktreeinclude` are not guaranteed to move, and snapshots/restoration do not prove that all external state or credentials are recoverable. Source: [Worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees).

4. **IssueOps must preserve its stronger ownership boundary rather than mirror Codex worktree semantics.** This repo specifies one canonical worktree and active generation per execution, with mutation trust tied to the exact native actor, session/process receipt, canonical cwd, lifecycle ID, and generation (`.issueops/architecture/issueops.md:91-94`). Codex-managed detached worktrees and UI handoff are useful isolation/recovery patterns, but do not establish that actor identity or lease. Separately, IssueOps serializes read-modify-write spans across the state root with SQLite `BEGIN IMMEDIATE` (`.issueops/architecture/issueops.md:127`; `.issueops/architecture/runtime.md:44`). The CLI 0.160.0 notes mention avoiding SQLite stalls during connection setup/logging and reclaiming unused log DB pages in the background, plus caching parsed plugin manifests and reusing HTTP connections; those are implementation-specific optimizations, not measured gains or direct evidence about IssueOps's lock. **Certainty: high** for repository contracts and release-note text; **medium** for the design implication. **Applicability:** evaluate user-visible status/recovery separately from authority, and profile IssueOps state-span wait/hold time before changing its global serialization. **Counterevidence/limit:** Codex's SQLite changes concern its own databases; they do not show that IssueOps's locking is a bottleneck. Sources: [Codex CLI changelog](https://learn.chatgpt.com/docs/changelog); [.issueops/architecture/issueops.md:91-94](../../architecture/issueops.md); [.issueops/architecture/runtime.md:44](../../architecture/runtime.md).
