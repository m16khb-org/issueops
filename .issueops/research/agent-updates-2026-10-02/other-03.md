# Cursor Background Agent Execution and Observability

**Retrieved:** 2026-10-02
**Scope:** One bounded evidence lane for IssueOps performance, optimization, and visibility. Cursor does not publish semantic versions for these entries; release dates identify the product updates. Sources below are public, official Cursor pages fetched on the retrieval date.

## Findings

1. **Move repeatable setup out of each agent's critical startup path.** On **2026-08-13**, Cursor released Cloud Agent Builds: environment preparation (repository clones, dependencies, install commands) is snapshotted ahead of runs, and warm copies let agents start from a ready environment. Cursor reports its own environments booting **10x faster** and reaching first token **3x faster**; this is a vendor-reported internal result, not an independently measured benchmark. The same release retains the last successful build if a new build fails, and exposes build status, logs, commit SHAs, and the build used by each run. The current Builds documentation explains the lifecycle and provenance in more detail. Sources: [2026-08-13 changelog](https://cursor.com/changelog/08-13-26) (release claim, single-source); [Cloud Agent Builds documentation](https://cursor.com/docs/cloud-agent/builds) (mechanism and traceability, official documentation corroboration from the same publisher). **Certainty:** high for shipped workflow and documented UI; low-to-moderate for performance magnitude outside Cursor's environment. **IssueOps applicability:** measure repeated setup costs and identify safe, idempotent preparation that can be reused; retain exact input/version provenance and last-known-good fallback. Do not import Cursor's speedup percentages as an IssueOps forecast. **Counterevidence/limits:** builds are Cursor-hosted Cloud Agent infrastructure; documented behavior does not establish equivalent gains for local sessions. Cursor gives no benchmark method or external replication on the release page.

2. **Background work is becoming event-resumable, not merely detached.** The **2026-08-19** Cloud Agents and harness update adds subscriptions to PRs, Slack threads, and schedules: a cloud agent can end its turn, wake on a matching event, and continue in the same conversation. Cursor says agents subscribe to PRs they create, address CI failures and review comments, and offers isolated cloud machines for subagents. The update also lets users steer a running agent without interrupting its current tool call. Sources: [2026-08-19 changelog](https://cursor.com/changelog/08-19-26) (feature release, single-source); [Cloud Agent capabilities documentation](https://cursor.com/docs/cloud-agent/capabilities) (subscription lifecycle, coalescing, event classes, and documented limits, same-publisher corroboration). **Certainty:** high for documented product behavior. **IssueOps applicability:** event-triggered continuation could reduce manual check-ins for bounded waits, but must remain subordinate to IssueOps' generation/actor fencing and explicit phase authority (`.issueops/architecture/issueops.md:1-2, 54`). **Counterevidence/limits:** subscriptions are currently Cloud Agent-only, last at most 180 days, and coalesce event bursts; GitHub CI auto-fix has eligibility limits and a 10-follow-up cap. These features do not imply that unattended mutation is safe for IssueOps.

3. **Make run diagnosis a first-class interface with structured evidence.** Current Cloud Agent documentation describes Cursor Cloud MCP diagnostics: run identity/status/source, lifecycle events, related runs, environment version and egress policy, transcripts, diff metadata, and setup logs. Its documented tools include `run-info`, `get-events`, `environment-info`, `list-cloud-agents`, and batched detail retrieval. Access is role-scoped: team admins can inspect eligible team runs, while non-admins see only their own. Sources: [Cloud Agent capabilities documentation](https://cursor.com/docs/cloud-agent/capabilities) (official current docs; not independently corroborated); [Cloud Agents overview](https://cursor.com/docs/cloud-agent) (overview references run diagnostics and artifacts, same publisher). **Certainty:** high for the documented diagnostics surface and access rules; actual availability depends on Cursor account/team configuration. **IssueOps applicability:** a compact, queryable run record linking lifecycle/status, events, environment, transcript, and diff could improve visibility without mixing telemetry into durable authority. Existing IssueOps distinguishes one-shot worker jobs from a long-running daemon (`.issueops/architecture/runtime.md:19`) and treats execution state as authoritative (`.issueops/architecture/issueops.md:1-2`); diagnosis should be additive and access-controlled. **Counterevidence/limits:** the docs describe inspectable evidence, not published latency/SLO dashboards or a general metrics export. Transcript access has permission boundaries, and the docs do not claim that telemetry improves execution correctness by itself.

## Source classification and evidence boundary

All product claims above are **official single-source claims** from Cursor. Where a release note and Cursor documentation both describe a feature, that is same-publisher corroboration, not independent corroboration. No independent source was used to validate Cursor's release claims or performance numbers. The recent evidence window (last 90 days before retrieval) contains directly relevant August 2026 updates; older Cursor material was unnecessary for these findings.

## EXPAND

- Compare IssueOps setup/startup time by phase and identify repeated work before proposing a cache or prepared-environment mechanism; record environment/config and input revision so results are attributable.
- Check existing IssueOps status, worker, and lifecycle projections for missing run-event and duration fields before proposing an observability surface. Keep diagnostics separate from generation-fenced write authority.
- If pursuing event-resumable work, specify subscription expiry, duplicate/coalesced event handling, cancellation, and actor/generation revalidation before any resumed mutation.
