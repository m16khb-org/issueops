# MCP Progress, Cancellation, and Observability Evidence

**Retrieved:** 2026-10-02
**Scope:** Public official sources and repository evidence; no implementation changes.

## Findings

1. **The final MCP revision `2026-07-28` reverses the old HTTP disconnect rule.** For Streamable HTTP it removes the `initialize` handshake, standalone GET streams, session IDs, `Last-Event-ID` replay, and client `notifications/cancelled` for ordinary requests: closing the request's SSE response **MUST** cancel it. Change events now use POST `subscriptions/listen`; per-request metadata and `Mcp-Method` plus method-specific `Mcp-Name` headers must match body fields. Stdio still requires explicit `notifications/cancelled`; the `2025-11-25` HTTP binding instead says disconnect is not cancellation. **Certainty: high** (normative versioned specs; MCP announcement and spec share one authority). **Applicability: high to transport-specific tests.** IssueOps' measured handshake returned `2025-11-25` (`.issueops/research/agent-updates-2026-10-02/mcp-baseline.md:18-19`); source wires stdio (`cmd/issueops/mcpcli/mcp_transport.go:13-26`), and its EOF drain removes cancelled IDs (`cmd/issueops/mcpcli/mcp_stdio_drain.go:37-45`). Do not apply HTTP disconnect semantics to this stdio path. **Counterevidence:** `2025-11-25` remains a compatibility version, and the latest spec preserves explicit cancellation on stdio. Sources: [MCP `2026-07-28` final release](https://blog.modelcontextprotocol.io/posts/2026-07-28/), [current Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), [current cancellation](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation), [current stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio), [previous transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

2. **Progress is optional telemetry, not a performance guarantee.** A client opts in with a unique active `progressToken`; servers MAY send updates, values MUST increase, updates MUST stop at completion, and peers SHOULD rate-limit. Progress may reset an idle timeout, but implementations SHOULD enforce a maximum timeout. On stdio, progress shares stdout and correlates by token. **Certainty: high** (normative MCP text). **Applicability: medium-high** for long MCP calls. It enables duration, stage, and cancellation observation but defines no guaranteed cadence, truthful percentage, or speedup. **Counterevidence:** servers may send no updates, so silent calls still need timeout handling. Sources: [progress](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/progress), [cancellation](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation), [stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio).

3. **Protocol Logging is deprecated; it differs from diagnostics and tracing.** Release `2026-07-28` deprecates Logging for at least twelve months. While retained, `notifications/message` is per-request: `_meta.io.modelcontextprotocol/logLevel` is required before a server may emit it. The spec recommends stderr for stdio and OpenTelemetry for structured observability. IssueOps disables the Logging capability and tests that contract (`cmd/issueops/mcpcli/mcp_sdk_server.go:58-62`; `cmd/issueops/mcpcli/mcp_sdk_server_test.go:204-213`). Its daemon path demotes repetitive SDK lifecycle events; source records 99.9% of a 270,000-line sample as routine, not a latency benchmark (`cmd/issueops/mcpcli/mcp_daemon_logfilter.go:11-25`; `internal/domain/daemonlog/routine.go:11-18,52-60`). **Certainty: high** for spec and code; the sample is repository-reported, not remeasured. **Applicability: high** to log signal/noise. **Counterevidence:** deprecation is not immediate removal; stdio clients may ignore stderr, which is not an error channel. Sources: [MCP Logging](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/logging), [MCP stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio).

4. **Keep protocol version, transport, SDK/client compatibility, and publication distinct.** `go.mod:28` pins Go SDK `v1.6.1` (published 2026-05-22). SDK `v1.7.0` (2026-07-28) explicitly supports MCP `2026-07-28` and says stateful HTTP negotiates down to `2025-11-25`. That release does not establish IssueOps or host-client support: the recorded IssueOps handshake remains `2025-11-25` (`mcp-baseline.md:18-19`), and source uses `mcp.IOTransport` (`cmd/issueops/mcpcli/mcp_transport.go:13-26`). **Certainty: high** for pin, dates, and recorded probe; host compatibility is unverified. **Applicability: high** to readiness decisions. **Counterevidence:** SDK `v1.7.0` retains backward compatibility; an SDK upgrade alone does not imply a transport change or a new IssueOps publication. Sources: [v1.6.1 release metadata](https://api.github.com/repos/modelcontextprotocol/go-sdk/releases/tags/v1.6.1), [v1.7.0 release](https://github.com/modelcontextprotocol/go-sdk/releases/tag/v1.7.0), [v1.7.0 release metadata](https://api.github.com/repos/modelcontextprotocol/go-sdk/releases/tags/v1.7.0).

## Independent corroboration

OpenTelemetry's independently maintained MCP conventions are **Development** status, not normative MCP requirements. They recommend method/JSON-RPC-ID correlation, protocol and transport attributes, and operation-duration histograms; they warn that arguments and results may be sensitive. This offers a visibility design lead, not evidence IssueOps emits these signals or gains performance from them. Source: [OpenTelemetry MCP semantic conventions](https://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/docs/gen-ai/mcp.md).

## EXPAND

- Verify protocol versions negotiated by supported Codex, Claude, and Omo clients separately from the server's stdio transport; the repository probe covers only one binary/client exchange.
- Check whether an SDK upgrade and each host client support the same revision before any rollout; `v1.7.0` is evidence of Go SDK support, not deployment readiness.
- If measuring MCP visibility, prototype low-cardinality operation duration, method, protocol version, transport, completion/cancellation outcome, and progress-event count. Keep arguments and result payloads out of telemetry unless redaction is explicitly verified.
