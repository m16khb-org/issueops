# Codex release evidence: performance, optimization, and visibility

**Retrieved:** 2026-10-02
**Scope:** Public official Codex CLI releases and dated changes, as one evidence lane for issueops.
**Latest stable found:** Codex CLI **0.160.0**, dated **2026-10-01**. The official changelog also lists 0.159.3 (2026-09-30) and 0.159.2 (2026-09-29); newer entries visible on GitHub include alpha prereleases, not stable releases. Certainty: high for the release/version/date as explicitly listed by OpenAI. This is a bounded retrieval, not a claim about unpublished or inaccessible artifacts.

## Findings

1. **SQLite contention and logging are treated as performance causes, with diagnostics preserved.** In 0.160.0, OpenAI says it prevented SQLite stalls during connection setup and logging, while surfacing initialization errors that had previously been masked as timeouts. PR #49032 explains the mechanism: configuring `auto_vacuum` on every connection could wait for a writer lock, and span entry/exit logging could block SQLx workers on undrained stderr while a write transaction was held. The change limits vacuum configuration to eligible databases and removes noisy span-boundary records while retaining busy/idle timings and explicit events. Its PR reports regression tests for writer-lock contention, blocked stderr, vacuum modes, and diagnostic retention. **Applicability:** issueops also uses SQLite with WAL and serialized state writes ([`.issueops/TECH_STACK.md`, “State 저장”](../../TECH_STACK.md#3-확정-라이브러리)). This supports profiling lock-span duration and logging performed inside critical spans, not importing Codex’s implementation. **Counterevidence/limit:** the release gives no measured latency improvement, and the PR describes Codex’s SQLx implementation; issueops’s Go/sqlite workload and actual bottleneck must be measured independently. **Certainty:** high for the change and stated rationale; unproven for issueops benefit.
   Sources: [0.160.0 release](https://github.com/openai/codex/releases/tag/rust-v0.160.0); [PR #49032](https://github.com/openai/codex/pull/49032).

2. **Repeated discovery work is optimized with bounded, invalidation-aware caching and connection reuse.** Also in 0.160.0, PR #49099 caches parsed plugin manifests across plugin workflows. The PR specifies a 128-entry bound, bypass above 64 KiB, content-digest/path-based reuse, rereads that retain edit visibility, retries after parse failures, and tests for isolation and invalidation. PR #49100 reuses a lazily initialized HTTP connection pool across a plugin configuration and its clones while preserving endpoint, SKU, and authentication behavior. **Applicability:** these are useful patterns if profiling shows repeated parsing or outbound connection setup in issueops’s optional adapters; cache lifetime, freshness, and isolation would need to fit the existing per-workspace/config rules. **Counterevidence/limit:** these are plugin-specific changes; neither establishes that issueops repeats comparable work, nor quantifies saved time. Do not add a cache absent a measured hot path. **Certainty:** high for implementation details as stated in upstream PRs; applicability is a hypothesis.
   Sources: [0.160.0 release](https://github.com/openai/codex/releases/tag/rust-v0.160.0); [PR #49099](https://github.com/openai/codex/pull/49099); [PR #49100](https://github.com/openai/codex/pull/49100).

3. **Long-lived history gets incremental retrieval rather than unbounded refresh.** PR #49106, included in 0.160.0, adds “Show more” pagination to the agent command center. The PR describes per-source cursors, buffering and merge-by-recency, retry/loading states, and limiting routine detail refresh to recent/loaded tasks plus explicitly targeted threads as history grows. It also lists regression coverage for pagination, retries, mixed sources, and removal races. **Applicability:** consider the same shape for issueops history/inspection surfaces only if evidence shows list or status latency scaling with retained records: cursor or bounded-page reads, and refresh only visible/relevant records. **Counterevidence/limit:** this concerns a UI task list, not issueops’s SQLite schema or CLI/MCP contracts; it is not evidence that issueops currently has a scaling problem. **Certainty:** high for upstream feature details; low-to-medium for transferability pending local profiling.
   Sources: [0.160.0 release](https://github.com/openai/codex/releases/tag/rust-v0.160.0); [PR #49106](https://github.com/openai/codex/pull/49106).

4. **Visibility improvements expose small durations and make older records discoverable.** The 0.159.0 changelog (listed in OpenAI’s official changelog on 2026-09-29) includes PR #48807, which changed completion footers from hiding known durations under 60 seconds to displaying every known duration, including `<1s`. The 0.160.0 “Show more” history feature above makes older tasks discoverable instead of silently limiting the list to ten. **Applicability:** issueops status/trace output can be assessed for whether it exposes elapsed time on short operations and whether bounded lists disclose continuation/older records. These are visibility candidates, not a request to copy TUI presentation. **Counterevidence/limit:** upstream reports presentation changes, not measured observability or user-outcome gains; issueops already has trace/status surfaces, so compare their actual output before proposing additions. **Certainty:** high for upstream behavior; issueops gap unverified.
   Sources: [official Codex changelog](https://developers.openai.com/codex/changelog); [PR #48807](https://github.com/openai/codex/pull/48807); [PR #49106](https://github.com/openai/codex/pull/49106).

## Source quality and EXPAND

OpenAI’s Codex changelog and `openai/codex` GitHub release/PR pages are official primary sources, but **not independent corroboration**: they are the same vendor’s publication surface. The changelog and release page agree on 0.160.0 and its listed changes; PRs provide implementation rationale and test descriptions, not independent validation. No external benchmark or independently reproduced performance result was found or used.

**EXPAND — actionable leads:** (1) profile issueops SQLite lock-span duration, connection setup, and logging behavior under concurrent state operations; retain correctness/error visibility in any optimization. (2) Measure repeated config/manifest parsing and remote client construction in actual issueops adapters before considering bounded reuse. (3) Benchmark status/history latency against increasing retained-record counts and inspect whether existing trace/status output reports short durations and truncation/pagination. **Reason:** upstream changes identify testable hypotheses, but do not demonstrate issueops bottlenecks or improvement; stop here until local measurements identify a candidate.
