# OpenHands Runtime Isolation and Evaluation

**Retrieved:** 2026-10-02
**Scope:** One bounded evidence lane for IssueOps performance, optimization, and visibility. OpenHands public official material and this repository only.

## Findings

1. **The latest verified OpenHands release is v1.24.0 (2026-09-25), but its notes do not announce a runtime-isolation or evaluation redesign.** The release lists product, UI, cloud, and maintenance changes; its runtime-adjacent item is a canvas fix that calls the agent-server runtime directly instead of the cloud proxy. Do not infer an isolation change from the version bump. **Certainty: high** for the release facts; **medium** for “latest” as a point-in-time page observation. **Applicability:** use the release stream as a dated change signal, not as runtime evidence. **Counterevidence:** release notes are selective summaries and do not prove that runtime internals were unchanged. Source: [v1.24.0 release notes](https://github.com/OpenHands/OpenHands/releases/tag/v1.24.0).

2. **OpenHands describes execution as backend-to-runtime communication with actions executed inside a Docker container, but this is a design claim, not an independent security assessment.** The official architecture page places the action execution server, shell, browser, and plugins in the container; backend and runtime communicate over REST. It attributes isolation, consistency, and resource control to the sandbox. It also documents bind and named volumes, including read-only and copy-on-write overlay options, so the boundary depends on configuration rather than container existence alone. **Certainty: high** that this is the documented architecture; **low** as evidence of resistance to hostile code. **Applicability:** IssueOps could make execution mode and boundary assumptions visible per run; borrowing OpenHands’ container model would exceed the current policy-gated read-only executor’s boundary. **Counterevidence:** no threat-model proof, isolation test results, or independent audit was found in the fetched official architecture source. This is an official single-source claim. Source: [OpenHands Runtime Architecture](https://github.com/OpenHands/docs/blob/main/openhands/usage/architecture/runtime.mdx), sections “Why do we need a sandboxed runtime?”, “How does the Runtime work?”, and “Volume mounts”.

3. **Runtime-image reuse is a concrete optimization pattern: progressively reuse source-, dependency-lock-, or version-tagged images before rebuilding from a base image.** The architecture documentation describes hashes based on runtime source and dependency inputs, allowing unchanged images to be reused and changed source to be copied onto a dependency-compatible image. This is a plausible way to reduce repeated setup work, but the page provides no measured build-time gain and uses older `v0.9.x` examples. **Certainty: medium-high** for the documented mechanism, **low** for its current implementation details or performance effect. **Applicability:** IssueOps may consider measuring cache hits and elapsed time around its own repeated checks before adding caching; this is a pattern, not a recommendation to adopt Docker. **Counterevidence:** the latest v1.24.0 notes do not confirm that these exact image tags remain current. Same official architecture source as finding 2, section “Image Tagging System” and “Build Process”.

4. **OpenHands separates benchmark execution from results presentation and records task-level evidence; its evaluation infrastructure is explicitly in migration.** The official `OpenHands/benchmarks` README says V0 benchmarks are migrating to the Software Agent SDK in V1, pins that SDK as a submodule commit for reproducibility, and lists local Docker and remote workspaces. Its SWE-Bench guide describes resumable runs, per-instance logs, worker counts, and evaluation using the official SWE-Bench evaluator. The separate results repository specifies scores, cost, average runtime, submission time, and optional per-instance outcomes. An example MiniMax-M2.7 SWE-Bench record reports score 75.6, average runtime 529 seconds, agent v1.14.0, submitted 2026-03-23; this is a dated model/run result, not a current OpenHands or IssueOps performance claim. **Certainty: high** for the repository’s stated schema and example; **medium** for currentness because the example predates retrieval by more than 90 days. **Applicability:** IssueOps visibility can benefit from tying metrics to exact versions/configuration and retaining per-task outcomes, cost/time, and resumable evidence. **Counterevidence:** the migration notice means benchmark compatibility is version-sensitive; the result source is OpenHands-maintained, not independent corroboration. The evaluator’s cited project, SWE-bench, is separate, but no second-party reproduction of this specific score was verified. Sources: [OpenHands Benchmarks README](https://github.com/OpenHands/benchmarks/blob/main/README.md), [SWE-Bench guide](https://github.com/OpenHands/benchmarks/blob/main/benchmarks/swebench/README.md), [results schema](https://github.com/OpenHands/openhands-index-results), [MiniMax-M2.7 scores.json](https://raw.githubusercontent.com/OpenHands/openhands-index-results/main/results/MiniMax-M2.7/scores.json).

## IssueOps fit

This evidence supports an optional measurement lane, not a core dependency or readiness gate. The repository’s `.issueops/TECH_STACK.md` §2.1 says the core must remain independent of companion tools and consume only verifiable boundaries; `.issueops/architecture/runtime.md` documents read-only policy execution and its process-group limitations. First improve observability of existing runs (version/config identity, duration, outcome, and retained evidence) and measure repeated setup/check costs. Consider external or containerized execution only as an explicitly optional adapter if a concrete workload justifies its added infrastructure and security model.

## EXPAND

- Inspect current OpenHands runtime implementation and security tests at a pinned release before making any isolation claim; the fetched docs’ GitHub source links to implementation files, but direct raw-file retrieval returned 404.
- Compare a small, fixed IssueOps task set with and without repeated setup reuse, recording elapsed time and outcomes. Do not extrapolate OpenHands model benchmark scores into this experiment.
