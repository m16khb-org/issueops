# Codex sandbox approvals and permission profiles

**Retrieved:** 2026-10-02
**Scope:** One bounded evidence lane for IssueOps performance, optimization, and visibility.
**Version context:** Official Codex CLI release `0.160.0` was published 2026-10-01 (`published_at` in [GitHub release metadata](https://api.github.com/repos/openai/codex/releases/tags/rust-v0.160.0)). The approval and permission pages are live, unversioned documentation; they do not state the release in which every current behavior shipped.

## Findings

1. **Sandbox and approval policy govern different things.** OpenAI’s current guidance says the sandbox technically limits filesystem and network capabilities, while approval policy specifies when execution pauses for permission. Its documented local default is workspace-limited writes with network disabled; `on-request` allows actions inside that boundary and prompts for actions such as network access or edits outside it. **Certainty: high** for the documented behavior, not pinned to a CLI build. **Applicability:** Treat a Codex approval as a boundary-crossing decision, not as a substitute for an execution sandbox, when evaluating IssueOps workflow friction. **Counterevidence:** In `0.160.0` notes, there is no quantified approval-friction or performance improvement; the release mentions restoring saved permissions when resuming sessions, which is a state/visibility detail rather than a measured speedup. Sources: [Agent approvals & security](https://learn.chatgpt.com/codex/agent-approvals-security); [0.160.0 notes](https://github.com/openai/codex/releases/tag/rust-v0.160.0).

2. **Permission profiles are Beta and conflict with the legacy sandbox configuration path.** The current permissions guide labels profiles “Beta,” documents built-ins `:read-only`, `:workspace`, and `:danger-full-access`, and allows custom profiles combining filesystem and network policy. It explicitly says to use either `default_permissions`/`[permissions]` or `sandbox_mode`/`sandbox_workspace_write`, not both: when legacy sandbox settings are present, they take precedence unless managed `allowed_permission_profiles` activates profile mode. **Certainty: high** as current documentation, version applicability unknown. **Applicability:** A scoped read-only or workspace profile could describe a repeatable Codex posture for IssueOps tasks, but should not be adopted as a stable cross-host contract while the feature is Beta. **Counterevidence:** Existing project architecture intentionally keeps host integration thin and core behavior host-neutral (`.issueops/architecture/host-integration.md:9-17`); no Codex permission-profile policy is established there. Source: [Permission profiles](https://learn.chatgpt.com/codex/permissions).

3. **A network allowlist does not constrain traffic unless network access and proxy enforcement are both active.** For profiles, `network.enabled = true` grants command network access, while `features.network_proxy = true` separately enforces domain rules. With network on and proxy off, commands have direct unrestricted outbound access; domains also do not govern hosted web search, MCP connections, apps/connectors, browser activity, or cloud tasks. **Certainty: high** for the documented distinction. **Applicability:** Visibility or optimization work should identify the surface being measured/controlled; a profile domain allowlist is not a general egress boundary. **Counterevidence:** Admin-managed `experimental_network` requirements can start proxy enforcement without the local feature toggle, so the toggle alone is not a complete policy inventory. Source: [Permission profiles—network permissions and scope](https://learn.chatgpt.com/codex/permissions#network-permissions).

4. **Approval visibility is instrumentable, but telemetry is opt-in and has a cost/privacy tradeoff.** The security guide documents OTel events for conversation starts (including sandbox/approval policy), tool decisions (approved/denied and source), tool results (duration and success), and network decisions. OTel export is off by default; prompt text is redacted by default, and the page advises controlled collectors and retention. It also says automatic approval review invokes additional model calls and can add usage. **Certainty: high** for the documented event fields and stated overhead, but no measured overhead amount is supplied. **Applicability:** These events could provide evidence on approval frequency and command duration before tuning an IssueOps/Codex workflow. The local integration here is a `SessionStart` context hook invoking IssueOps (`configs/codex/hooks.json:2-13`), not documented as consuming Codex OTel. **Counterevidence:** Telemetry is not enabled by default and tool-result duration alone does not establish end-to-end workflow latency. Source: [Agent approvals & security—Auto-review and OTel](https://learn.chatgpt.com/codex/agent-approvals-security).

## Evidence classification

Official OpenAI documentation and official OpenAI Codex release notes are single-source vendor claims. The release metadata corroborates the `0.160.0` publication date but is part of the same GitHub/OpenAI release record, not independent corroboration. Repository anchors establish only IssueOps’s own integration shape. No independent source or benchmark was used; no performance percentage is claimed.
