# OmO installed package, upstream, and update evidence

**Retrieved:** 2026-10-02

**Scope:** Public official sources and installed package/launcher behavior. This is one evidence lane for IssueOps performance, optimization, and visibility, not a benchmark of IssueOps itself.

## Findings

1. **Identity and distribution channel.** The installed package at `$HOME/node_modules/omo-ai/package.json:2-14` identifies itself as `omo-ai` version `5.1.8`, exposes the `omo` command, and names `https://github.com/code-yeongyu/oh-my-openagent` as its repository. The upstream README and installation guide confirm that OmO Native is the standalone `omo` command distributed as `omo-ai`, distinct from the OpenCode and Codex editions. The GitHub README also cautions that the unrelated npm package named `omo` is not this project. At retrieval, npm Registry metadata reported `latest: 5.1.9` and `beta: 5.1.0`; thus this local install lagged the published latest by one patch release. **Certainty: high. Applicability:** pin research and update checks to the `omo-ai` package and this repository, rather than the ambiguous `omo` name. **Counterevidence/limit:** local `package.json` describes this installation, not every machine; npm dist-tags are mutable. npm Registry is an independently hosted distribution record, but not independent editorial corroboration of upstream claims.

2. **Current release facts and update delta.** Upstream `CHANGELOG.md` records OmO Native `5.1.8` on 2026-10-01 (engine `senpi 2026.10.1-2`) and `5.1.9` on 2026-10-02 (engine `senpi 2026.10.1-3`). GitHub's official release API independently confirms publication timestamps: `5.1.8` at `2026-10-01T15:00:33Z`, `5.1.9` at `2026-10-02T01:13:10Z`. Version `5.1.8` fixed a compiled-install `bun` subprocess being mistaken for a second agent, among other changes. `5.1.9` fixes a Windows x64 first-Python-cell cold-start failure and delegated tasks losing configured timeout/retry values; it also prevents invalid thinking-level variants from flooding `fallback.log` with warnings. **Certainty: high for versions, dates, and documented change claims; medium for end-user impact absent local reproduction. Applicability:** evaluate upgrade-sensitive subprocess, delegation settings, and diagnostic-noise behaviors when IssueOps depends on Omo. **Counterevidence:** upstream release notes are maintainer-authored; the release API confirms publication metadata, not the fixes themselves. No independent reproductions were used.

3. **A concrete performance and observability precedent.** OmO `5.1.1` (2026-09-29) separated task children onto per-session engine hosts. Its changelog reports measured trade-offs: with four parent sessions and four children each, 2.7 GB RSS / 0.8 GB physical footprint versus 0.78 GB / 0.24 GB on one shared host; idle per-session host footprint was 126 MB versus 137 MB for the old shared host. Prewarming reduced task-call-to-first-model-request from 1666/3280 ms (p50/p95) to 1116/1678 ms, compared with 979/1593 ms when the shared host was already running. The same release added daemon/doctor visibility for host PID, sessions, memory, and crash count. **Certainty: high that upstream published these measurements and observability fields; medium that results generalize beyond the stated setup. Applicability:** useful pattern for IssueOps: report latency and resource cost together, and expose per-worker health rather than optimizing a single metric. **Counterevidence:** these are upstream's own measurements, not independently reproduced, and separate-host isolation increased memory use; they do not establish an IssueOps bottleneck or expected gain.

4. **Low-cost work reduction without unsupported speed claims.** OmO `5.1.5` (2026-09-30) says memory recall changed from one Git process per note to one Git batch per reload to avoid machine slowdown with many sessions. `5.1.6` (2026-09-30) describes reuse of QA/review evidence per target, while rerunning affected tests and a complete final verification. The installed launcher also documents a Bun-global fast path: `$HOME/node_modules/omo-ai/bin/omo.js:8-19` repairs a shim and re-executes under Bun; `$HOME/node_modules/omo-ai/bin/lib/bun-bin-shim.js:25-40` says that shim avoids a Node boot. **Certainty: high for documented implementation and change intent; no independent performance measurements for these changes. Applicability:** inspect repeated process startup and redundant evidence collection in IssueOps, but preserve correctness checks. **Counterevidence:** upstream gives no quantified recall or shim speedup; the shim path only applies to POSIX Bun-global installs.
