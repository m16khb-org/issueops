# Cline checkpointing hooks and observability

Retrieved: 2026-10-02. Scope: public official Cline sources and this issueops checkout. Cline's newest releases observed were [desktop v4.1.22](https://api.github.com/repos/cline/cline/releases/tags/v4.1.22) and [SDK v0.0.89](https://api.github.com/repos/cline/cline/releases/tags/sdk/sdk/v0.0.89), both published 2026-09-30. Checkpoint-specific changes discussed below shipped earlier in SDK v0.0.83 (2026-09-15) and v0.0.84 (2026-09-22). Confidence is high for release dates and described behavior, based on official release records and source; confidence is medium for transferability to issueops. Release notes and source are from the same publisher, not independent corroboration. No independent performance study was found or used.

## Findings

1. **Checkpoint timing is narrower in implementation than user-facing docs imply.** Cline's checkpoint guide says it saves after each tool use, captures untracked files, and warns snapshots may slow large repositories ([official guide](https://docs.cline.bot/core-workflows/checkpoints)). The current SDK implementation instead hooks the root agent's first model iteration for a user run, uses persisted checkpoint history to avoid duplicate snapshots on resume, and records a snapshot before model work ([checkpoint-hooks.ts](https://raw.githubusercontent.com/cline/cline/main/sdk/packages/core/src/hooks/checkpoint-hooks.ts)). The discrepancy matters: checkpoint granularity and cost should be established from implementation, not the simplified guide. **Applicability:** issueops could benchmark its own actual boundary before adding any hook work. **Counterevidence:** Cline's extension may have host-specific behavior beyond the SDK source; neither source establishes issueops should adopt repository snapshots.

2. **Cline optimized repeat snapshots with a persistent per-session Git index.** SDK v0.0.83 says each turn previously re-hashed all untracked files, potentially blocking work in multi-GB workspaces; the release introduced a persistent index whose Git stat cache avoids re-reading unchanged files, claims the second and later snapshots take about one Git process, and rebuilds once after index corruption/stale lock. Snapshot bytes remain unchanged ([SDK v0.0.83 release, published 2026-09-15](https://api.github.com/repos/cline/cline/releases/tags/sdk/sdk/v0.0.83); [implementation](https://raw.githubusercontent.com/cline/cline/main/sdk/packages/core/src/hooks/checkpoint-hooks.ts)). **Certainty:** high that Cline shipped this design; medium for the performance magnitude, which is vendor-reported and workload-specific. **Applicability:** useful optimization pattern only if measurements show repeated hashing is an issueops hot path. **Counterevidence:** the official checkpoint guide explicitly warns snapshots can slow large repositories; the optimization does not remove cold-index or changed-file cost.

3. **Snapshot telemetry names outcomes and duration while excluding workspace paths/content.** Current `checkpoint-hooks.ts` describes and emits one `checkpoint.snapshot` event per built-in attempt with `outcome` (`stash`, `head_clean`, `head_fallback`, `skipped`) and `durationMs`; comments explicitly exclude paths and file contents. Event properties also include session ID and run count. This gives operators a way to separate normal clean checkpoints from degraded fallback without collecting diffs. The linked `main` source is current as retrieved, but I found no release note assigning this event to a specific tagged version; latest SDK tag observed was v0.0.89, 2026-09-30. **Applicability:** issueops could measure duration and outcome at a verified boundary, preserving its existing data minimization. **Counterevidence:** no public dashboard, sampling policy, or independent validation of event delivery was established by the fetched source.

4. **Hook observability is paired with opt-in blocking, not imposed on every run.** SDK v0.0.84 (published 2026-09-22) added run-start context injection and optional `blockingRunStartHooks`; blocking defaults off to avoid stalling existing scripts. It also reports detached hook runtime, with an observation window capped at 30 seconds. The same release says `afterModel` receives a request ID for correlation with a Git snapshot, and preserves Langfuse user/session trace attribution ([SDK v0.0.84 release](https://api.github.com/repos/cline/cline/releases/tags/sdk/sdk/v0.0.84)). **Applicability:** distinguish synchronous context hooks from asynchronous measurement, and correlate observations with stable operation IDs. **Counterevidence:** this is Cline SDK agent-runtime functionality, not evidence that issueops native host hooks support the same callbacks or should gain blocking hooks.

## issueops fit

Issueops deliberately keeps default hooks context-only: `RunHook` dispatches only `session-start` and `post-compact`, rendering the static project-doc catalog; it does not touch durable state, telemetry, or IssueOps authority (`cmd/issueops/hookcli/hook.go:19-43`; `.issueops/AGENT_WORKFLOW.md:66-69`). The 2026-08-27 ADR documents removal of lifecycle/metrics hooks and cites a prior unregistered hook cost as a reason not to preserve that surface (`.issueops/adr/decisions/2026-08-27-session-start-owns-compaction-context.md`). Therefore, Cline is an evidence lane for profiling and bounded observations, not a recommendation to restore lifecycle hooks. Existing issueops ADR on external LLM usage likewise makes observations best-effort and defers regression comparisons until baselines exist (`.issueops/adr/decisions/2026-07-02-external-llm-usage-observation.md`).

## EXPAND

- Benchmark issueops context-hook cost and repeat-run variance on representative small and large repositories before considering any work in that path; reason: Cline's index optimization is workload-specific, and issueops intentionally avoids runtime telemetry in default hooks.
- If a measured issueops hot path repeatedly hashes unchanged files, inspect whether a persistent index can preserve the current correctness and isolation invariants; reason: Cline reports a repeat-run optimization but offers no independent benchmark or issueops-specific result.
