# Codex app-server sessions and event streaming

**Retrieved:** 2026-10-02
**Scope:** One evidence lane for IssueOps performance, optimization, and visibility. Public official Codex sources and this repository only.
**Release context:** Codex CLI `0.160.0` was published 2026-10-01 (`published_at` in the [official GitHub Releases API](https://api.github.com/repos/openai/codex/releases/tags/rust-v0.160.0)). The [release notes](https://github.com/openai/codex/releases/tag/rust-v0.160.0) include an incremental running-turn tracking change (#49084), but no quantified performance claim. App-server examples currently name GPT-6.1 Sol; the protocol documentation is a live upstream document, not pinned to this CLI release. Findings below describe the documented contract, not a tested integration against 0.160.0.

## Findings

1. **App-server is a stateful, bidirectional JSON-RPC surface, not a one-shot command wrapper.** Each connection requires `initialize` then `initialized`; clients create/resume/fork threads and start turns, then continue reading notifications on the same transport. The official guide describes stdio JSONL as the default, Unix sockets as supported, and WebSocket as experimental/unsupported for production. Certainty: **high** for documented contract; **official single-source** (OpenAI developer docs). Applicability: a future native Codex visibility adapter could hold one connection and correlate request IDs, thread IDs, and turn IDs. Counterevidence: OpenAI explicitly directs CI/job automation to Codex SDK rather than app-server; app-server’s remote/WebSocket route is not production-supported. Source: [Codex app-server guide](https://developers.openai.com/codex/app-server), sections “Supported transports,” “Initialize once per connection,” and “Start (or resume) a thread.”

2. **Progress is available as granular notifications, with explicit terminal turn status.** A `turn/start` acknowledgement is followed by thread/item events including `item/started`, `item/completed`, `item/agentMessage/delta`, tool progress, and finally `turn/completed`; `turn/interrupt` ends the turn as interrupted. `thread/status/changed` reports loaded-thread state and active flags (including waiting on approval). This is directly useful for operational visibility (started/running/waiting/completed/interrupted/error) without inferring state from terminal text. Certainty: **high** as documented API behavior; **official single-source**. Counterevidence: the docs do not promise event delivery latency, retention guarantees for live notifications, or that every internal action has a public progress event. Source: [Codex app-server guide](https://developers.openai.com/codex/app-server), “Stream events,” “Finish the turn,” and “Track thread status changes.”

3. **The protocol exposes backpressure rather than promising unlimited throughput.** In WebSocket mode, bounded ingress queues reject requests when full with JSON-RPC `-32001` (“Server overloaded; retry later”); the client guidance says exponential backoff with jitter. This is concrete evidence to design bounded queues, overload counters, and retry-safe request handling if IssueOps ever consumes a stream. It is not evidence that the app-server is faster than spawning CLI processes. Certainty: **high** for documented WebSocket behavior; **official single-source**. Counterevidence: this limit is specified for WebSocket mode, which is experimental; do not generalize it to stdio or Unix sockets without code-level verification. Source: [Codex app-server guide](https://developers.openai.com/codex/app-server), “In WebSocket mode, app-server uses bounded queues.”

4. **Thread lifecycle can support resource-conscious observation and history reads.** `thread/start` subscribes the connection to that thread’s turn/item events; `thread/read` can fetch stored history without resuming/subscribing; `thread/unsubscribe` removes a subscription and may eventually unload an inactive thread when no subscribers remain. `thread/list` and item/turn pagination support later inspection. This suggests separating live event consumption from retrospective reporting, and explicitly unsubscribing when observation ends. Certainty: **high** for stated behavior; **official single-source**. Counterevidence: exact inactivity grace periods and persistence behavior are implementation details subject to upstream change; live events are not themselves an IssueOps durable audit ledger. Source: [Codex app-server guide](https://developers.openai.com/codex/app-server), “Read a stored thread,” “Unsubscribe from a loaded thread,” and history-list methods.

5. **This repository intentionally lacks a host-event telemetry path today.** Its Codex integration is documented as user-scope skills, MCP, and a `SessionStart` context hook, while runtime docs identify that integration as implemented with no app-server stream adapter (`.issueops/architecture/host-integration.md:13`, `.issueops/architecture/runtime.md:20`). The hook contract explicitly excludes runtime diagnostics and telemetry (`.issueops/AGENT_WORKFLOW.md:68`); a recorded decision also rejects restoring unused legacy diagnostic/metrics hooks (`.issueops/adr/decisions/2026-08-27-session-start-owns-compaction-context.md:5-12`). Certainty: **high** for repository’s documented architecture; **local source**. Applicability: app-server events could be evaluated as a separate optional host adapter, but should not be put into the context-only hook or treated as a replacement for IssueOps state authority. Counterevidence: current project docs do not establish a need, owner, or measured bottleneck for this integration. These local sources are not independent corroboration of OpenAI’s claims.

## Evidence independence and limits

The official developer guide and `openai/codex` documentation/release notes are all first-party OpenAI evidence; they are not independent corroboration. The repository anchors establish only IssueOps’s own documented boundary. GitHub issue [#11166](https://github.com/openai/codex/issues/11166) is a user feature request, not authoritative protocol documentation, and was not used to substantiate behavior. No performance percentages are asserted. The older [`protocol_v1.md`](https://github.com/openai/codex/blob/main/codex-rs/docs/protocol_v1.md) explicitly warns that implementation may differ and describes a different internal interface, so it is not treated as the current app-server contract.

## EXPAND

- Inspect the exact tagged `0.160.0` app-server schema/source and compare it with generated schemas from that binary before any implementation decision. The public guide is live and the 0.160 release notes do not establish a matching protocol revision.
- If visibility is a real requirement, prototype a read-only local stdio observer and measure startup cost, event volume, dropped/overload behavior, and lifecycle correlation against the existing CLI/MCP workflow. No IssueOps need or performance gain is evidenced yet.
- Revisit remote WebSocket support only if the use case requires cross-process/network attachment; the official guide labels it experimental/unsupported for production.
