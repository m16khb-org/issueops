# Claude Code permissions, sandboxing, and worktree isolation

**Retrieved:** 2026-10-02
**Scope:** Public official Claude Code sources and this repository; one evidence lane for IssueOps performance, optimization, and visibility.
**Version context:** Latest official release checked: `v2.1.287` (published 2026-10-01); comparison release `v2.1.260` (published 2026-09-03). The 2025 sandbox engineering post is older than 90 days and is included only for its explicit prompt-reduction claim.

## Findings

1. **Permission approvals and OS sandboxing are different controls.** The sandbox is off by default and constrains Bash, PowerShell, Monitor commands, and their child processes. Claude's file/web tools, hooks, local MCP servers, LSP servers, and helper processes run outside it under other permission or process controls. It is supported on macOS, Linux, and WSL2, not native Windows. **Certainty: high; official single-source (Anthropic docs). Applicability: high** when describing host-dependent policy and measuring prompt waits. **Counterevidence:** sandboxed commands can run without prompts in auto-allow mode, but that approval optimization does not extend the OS boundary to excluded tools. The docs specify permissions for those other surfaces; do not describe `/sandbox` as session-wide confinement. Sources: [sandboxing](https://code.claude.com/docs/en/sandboxing#what-runs-outside-the-sandbox), [permissions](https://code.claude.com/docs/en/permissions).

2. **Claude worktrees provide guarded checkout isolation, not independent repository state.** Claude documents checks that block file edits targeting the main checkout, commands whose working directory resolves there, Git redirection there, and command shapes whose Git target cannot be verified; the checks also cover subagents. However, a worktree shares the repository's `.git` directory, and sandboxing allows writes there for operations such as commits. “Yes, and don't ask again” Bash approvals in a worktree are saved to the main checkout's `.claude/settings.local.json` and apply across that repository's worktrees. Git independently documents linked worktrees as sharing repository data except per-worktree files such as `HEAD` and `index`. **Certainty: high. Applicability: high**: IssueOps already fences authority by lifecycle ID, generation, process receipt, and canonical worktree (`.issueops/architecture/issueops-cleanup.md:7-15`); a Claude-created worktree alone is not a lease or authority boundary. **Counterevidence:** independent working directories do prevent ordinary file edits from colliding; shared metadata does not negate that concurrency benefit. Sources: [Claude worktrees: isolation checks](https://code.claude.com/docs/en/worktrees#how-claude-code-enforces-isolation), [Claude worktrees: shared state](https://code.claude.com/docs/en/worktrees#what-worktrees-share-with-the-main-checkout), [Git worktree docs](https://git-scm.com/docs/git-worktree). Git is independent corroboration for Git semantics only, not a security review of Claude's implementation.

3. **Sandbox defaults are narrower than “worktree-only access” in some dimensions and broader in others.** Sandboxed commands may write to the working directory, per-user temp directory, and added directories; by default they may read most of the machine, including credential files. With a linked worktree, the sandbox also permits writes to the main repository's shared `.git` directory (but denies writes to its `hooks/` and `config`). `permissions.blockReadsOutsideWorkingDirectories` can narrow reads. **Certainty: high; official single-source. Applicability: high** for command-boundary design and tests. IssueOps should not infer root isolation from the shell cwd or assume every child-process read is workspace-local. **Counterevidence:** these defaults are configurable; credential deny/mask settings and filesystem rules can narrow access. Sources: [sandbox filesystem isolation](https://code.claude.com/docs/en/sandboxing#filesystem-isolation), [Git worktree docs](https://git-scm.com/docs/git-worktree).

4. **Recent release notes give concrete visibility and reliability signals, not IssueOps performance evidence.** `v2.1.260` (2026-09-03) added `/diff` for uncommitted edits and fixed parenthesis-containing permission paths being ignored by the Bash sandbox, which could leave nominally read-only folders writable. `v2.1.287` (2026-10-01) fixed `claude agents` sometimes hiding a background session's pending permission prompt and a Linux sandboxed Bash executable-handle issue. **Certainty: high; official single-source (Anthropic release records). Applicability: medium-high** for visibility and compatibility probes. Separately, Anthropic's 2025-10-20 engineering post reports an 84% reduction in permission prompts in its internal usage. This is an Anthropic self-report, not independently corroborated and not an IssueOps benchmark. **Counterevidence:** neither release notes nor the post establish IssueOps wall-time, throughput, or success-rate gains. Sources: [v2.1.260](https://github.com/anthropics/claude-code/releases/tag/v2.1.260), [v2.1.287](https://github.com/anthropics/claude-code/releases/tag/v2.1.287), [Anthropic sandbox engineering post](https://www.anthropic.com/engineering/claude-code-sandboxing).

## Source assessment

Product and release claims above come from Anthropic's official docs, engineering post, and `anthropics/claude-code` release records. These are primary sources from one publisher, not independent confirmation of Claude behavior. Git's official documentation independently corroborates only Git's shared-metadata model. No measured IssueOps effect is claimed.
